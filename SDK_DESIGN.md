# IQ SDK: design

A proposal for `neuron-core/iq-php-sdk`, the package that connects Neuron AI workflows and agents to IQ. Milestones 0 to 6 of appendix D are implemented and tested. The first six are the whole core package and a platform simulator that drives it over real HTTP: the public types, the ledger, the runner, the two test fakes, the protocol schemas, the local path (`workflow()`, `start()`, `submitInputs()`, `signal()`, `recover()`, `run()`, `events()`, `dispatch()`), and the signed endpoint with App Sync (`handle()`, `sync()`). The seventh is the Laravel bridge of section 10, which is built and tested in its own repository. The Symfony bridge and everything that needs a real platform are still a proposal.

- **Builds on:** [DURABLE_PLATFORM_READINESS.md](DURABLE_PLATFORM_READINESS.md) and the decisions in its section 12.
- **Requires:** `neuron-core/neuron-ai ^4.1.26` (typed refusals, the snapshot fields, a late copy of a continuation refused as stale in every interleaving, the tag a start gives its run, a tool call that runs at most once, and the dataset an evaluation result names).
- **Date:** 2026-10-28
- **Reading path:** sections 1 to 8 are what you need to approve the design. Section 9 onwards and the appendices are for building it.

## 1. The design in one page

Your workflow runs in your application and keeps its data in your database. IQ keeps a list of your runs and a clock. When a run stops to wait (for a timer, for an event that your application will deliver, or for a retry after a failure), the SDK tells the platform what the run is waiting for. When a timer or a retry comes due, the platform calls one signed URL in your application. The SDK puts that call on your queue, a worker continues the run through Neuron, and the SDK tells the platform what the run looks like now. When your own code starts or answers a run, it goes through `$iq->workflow()`, so the platform hears about that run too. Any call can arrive twice or late: Neuron and the SDK refuse the copy. If the platform hears nothing, it asks. Your database is always right.

Five rules carry everything else.

1. **Your store is the truth.** The platform holds a copy of identifiers and statuses, and reads the truth again whenever it is unsure.
2. **The platform sends three orders: start a run, wake a run and, only when a person asks for it, abandon a run.** It can also ask two questions: inspect a run, ping the endpoint. Nothing else comes in.
3. **Every execution says "starting", then "this is the run now".** These are the announcement and the report. A queue worker sends them directly. A web request hands them to your queue, so no call to the platform ever sits on a user's request.
4. **A start runs at most once.** The SDK writes every start that arrives through a queue or over the wire into a small ledger in your store, and refuses a second copy, even after the run has finished and its records are gone.
5. **The platform owns retries.** Your queue runs each segment once, and a retry is a new wake sent by the platform. The only messages your queue retries are the SDK's own notices to the platform, which run no workflow code, and a start, an answer or a signal of your own that was aborted before any workflow code ran, for the reasons 9.5 lists.

**What it costs.** A queue and a worker become mandatory, also for an application that only streams chat inside requests, and a request fails when the queue is down. A start that travels through a queue runs once or not at all. The SDK keeps one small row per workflow ID in your workflow store, and refuses `FilePersistence` and `InMemoryPersistence`. The signing key alone can start runs. Queue retries are off for segments: the platform's retry policy replaces `$tries`. Section 6 has the details.

### What crosses the wire

| Reaches the platform | Never leaves your application |
|---|---|
| Definition names and versions, your endpoint URL | Workflow state, step results, memos |
| Workflow IDs, run IDs, attempt numbers | Start inputs, prompts, messages |
| A status or an outcome: running, suspended, failed, completed | Answers, approvals, event payloads |
| For a wait: its number, its type, the event name, the time to wake | The text and the tool inputs of an approval request |
| The lease deadline of a running run | Exception messages and traces |
| The class name of an exception | Results |

Workflow IDs and event names do reach the platform, so they must not contain secrets. A thread ID built from a user ID is personal data there. The name of the definition that started a run reaches the platform with every run it is shown, read from the run's tag. A tag that code outside the SDK set reaches it too when it has the form of a definition name, and only then.

Two things send more, and each only when you turn it on. With `enableTracing()` the trace of every segment the SDK executes reaches the platform, and so does the trace of every run of an agent or a workflow your application runs itself with a listener from `tracer()` subscribed: the names of nodes, tools and models, token counts, the message and the stack trace of an exception and, unless you turn content capture off, prompts, completions, tool arguments and tool results. With `evaluationOutput()` listed in `evaluation.php`, the results of an evaluation reach it, with the input and the output of every dataset item. 9.9 says what each one sends. A dataset an evaluator reads with `dataset()` sends nothing but its slug.

### Vocabulary

| Term | Meaning |
|---|---|
| Definition | A workflow or agent class registered under a name and a version |
| Workflow ID | The stable address of a workflow (`order:123`, a chat thread). It holds one run at a time |
| Run ID, attempt | One execution, and a counter Neuron raises each time a process takes that execution over |
| Segment | One uninterrupted stretch of a run, until it suspends, completes or fails |
| Fence | The run ID and attempt a wake or an answer carries. Neuron refuses it when they are no longer current |
| Lease | A time-limited claim on a running run. When it expires, another process may take the run over |
| Wake | An order with no input: Neuron decides whether a timer is due or a failed or dead run must be finished |
| Snapshot | What `inspect()` reads from your store: the run holding a workflow ID, or nothing |
| Tag | A label Neuron stores with a run when the run starts, and never reads. The SDK sets it to the name of the definition that started the run |
| Ledger | The SDK's list, in your store, of the starts it has accepted |
| Invocation | One message in your queue: an order to execute one segment, or an announcement or an observe to post |
| Observe | A queued reminder: "read the store and tell the platform" |
| Manifest | The list of definitions and versions that the last `sync` published |
| Trigger, firing | What makes the platform start a run (a schedule, an API call), and one occurrence of it. Triggers are set up on the platform, not in the SDK |
| Operator | A person acting on the platform, through its dashboard or API |
| Retry policy | How many times, and how far apart, the platform wakes a failed or dead run before it gives up and alerts. It is a setting kept on the platform: `register()` has no retry argument and the protocol carries none. It replaces the guides' `$tries`. Its values are not designed in this document |

## 2. Questions for you

Each is a decision that is yours. Where a question has them, the recommendation comes first, then its cost, then what a "no" means.

1. **The public API of section 4.** Confirm the names: `IQ` with `register()`, `setPersistence()`, `setDispatcher()`, `sync()`, `handle()`, `invoke()`, `workflow()`; `ManagedWorkflow`, `PendingSegment`, `DispatcherInterface`, `Invocation`, `Report`, `SyncResult`, the enums `Verb`, `Outcome`, `Code`, and `IQException`; `Testing\FakePlatform` and `Testing\FakeDispatcher` with the methods of appendix C; and in the bridges the config keys, the `InvocationSettled` event, the `iq:sync` command and the route `POST /iq`. One naming choice to check: `IQ::setPersistence()` takes a factory closure, as Neuron's `setResources()` and `setChannel()` do, where `Workflow::setPersistence()` takes an instance.

2. **The root after neuron-ai 4.1.5.** The Cloud sections left the guides, so this design has no `GuzzleTransport` and no `listener()`, `dataset()` or `evaluationOutput()`. Recommended. If they are coming back, they fit beside the rest on the same root.

3. **A ledger in the user's store, under a `__iq:` partition.** Recommended: it is what takes the platform out of correctness. The costs: two more store operations per queued start; one row of about 260 characters per workflow ID stays until the developer deletes it with a statement the guide gives; and the SDK writes its own records into a store whose interface says the engine owns all record semantics, under a prefix the engine keeps for itself, so core should reserve `__iq:` in one sentence. If no: the platform must remember finished runs and answer before every start, which is the first design (section 8).

4. **No completion retention under the SDK.** Recommended: fewer rules, and a chat thread is free the moment a turn ends. The cost: when a worker dies right after its last write, the platform cannot tell that the run finished and shows "ended, outcome unknown". If no: a release step, a rule for who releases what, and threads that can be held until the release.

5. **Web requests never call the platform.** A segment run in a request, like the chat turn of example (b), still executes in the request. Only the SDK's two notices to the platform (the announcement and the observe) go through your queue. Recommended for chat latency. The cost: two messages go on the queue per segment run in a request, and such a request fails when the queue is down. A durable queue and a worker are needed whatever you answer here, because every order from the platform (a wake that retries a failed turn, a timer, a start) is queued by the endpoint and executed by a worker (9.4). If no: one call of up to 3 seconds before a segment and one after it, on the user's request, whenever the platform is slow.

6. **A queued start runs once or not at all, and the platform never replaces a lost one by itself.** Recommended. The cost: a start that was claimed and did not run, or that is still unclaimed when its use-by time passes, waits for a person (section 6); a start your own code dispatched has no operator; and for a schedule whose workflow ID contains the date, the next firing does not make up for the lost one. Sending the same start again is part of v1 before the claim and within its use-by time, because the ledger stops any copy that did claim: the platform does so for its own when a report or an `inspect` shows it unclaimed (appendix B, rule 13), and the bridges do so for yours after the aborts listed in 9.5. A start that stays silent is not sent again: the platform asks about it only after its use-by time (appendix B, rule 12). Not in v1: queueing a start of yours again after its worker was killed or its job was lost. If no to the whole rule: the platform has to prove a start never ran before replacing it, and two ways to be wrong were reproduced.

7. **The platform retries a failed chat turn like any other run.** The retry rule has no exception. A turn that failed because the browser closed or the user pressed Stop is run again in a worker: the provider is paid again, the answer goes to the agent's channel and not to the closed response, and a message sent while that retry runs is refused with 409 until it ends. The guides today finish a turn that failed inside a request only when the next message arrives; a queued turn is retried by the queue (`$tries = 3`, Messenger's three retries). Decide before the guides are written: one rule for every run, as designed, or no platform retry for a run whose failed segment ran in a request.

8. **No events through the platform in protocol 1.** Your application delivers an event itself with `signal()`. One that arrives before its wait is refused and not kept, so the workflow looks the fact up before it waits. The platform starts runs from a schedule or its API, not from an event. Recommended for v1; the verbs `answer` and `signal` are reserved. This closes "event semantics" in section 12 of the readiness document.

9. **No payload in protocol 1.** A platform-started workflow loads its input from its workflow ID, and a platform-started agent builds its prompt in `startEvent()`. Recommended; the field `input` is reserved. If no: a hydrator and a validator in the SDK, and payload storage on the platform.

10. **The SDK's persistence and lease replace the class's own.** Recommended: a plain `Workflow` defaults to in-memory storage and no lease, and the SDK cannot read what a class declares. The cost: an agent that overrides `leaseTimeout()` for a slow tool is silently cut to the bridge's `lease_timeout`, which is one value for every definition listed in the config. A lease shorter than the slowest node lets a second worker take a live run, and the node in flight then runs twice. A definition that needs its own lease is registered in a provider with `register(..., leaseTimeout: ...)`. A public getter in core would let the SDK verify instead of override.

11. **Exception class names reach the platform**, never messages. Recommended: without them the platform cannot group failures or choose a retry policy.

12. **The signing key alone can start runs.** Whoever holds it can start any registered definition that starts without input, on any workflow ID. The platform cannot stop it, only alert afterwards. On a run that carries a tag, the key acts only through the definition that started the run: the SDK refuses a wake, an `inspect` or an `abandon` that names another definition (9.3). The limit remains for a run with no tag, which was started outside the SDK or by a version of the SDK that set none: a wake that names another definition continues such a run on that definition's nodes, and an abandon that names another definition skips the guard of an Agent. Recommended for v1: accept it. The alternative that keeps correctness local is the reserved per-definition switch `platformStart`, with which the SDK refuses a wire start for a definition that did not allow it.

13. **`recover()` before every agent turn in the guides.** Today `recoverFailedTurn()` is called only by the endpoints that run a turn inside the request (in the Symfony guide only before a new turn, not before a continuation); the endpoints that queue a turn do not call it, and the job or handler finishes a failed or dead run it meets. Recommended. It is a second retry path beside the platform's wake; the fence lets only one of the two execute.

14. **Bridge floors**: Laravel `^12.41 || ^13.0` on PHP 8.2 (question 23 says why 12.41), Symfony `^6.4` on PHP 8.1. Recommended.

Questions 15 to 22 came from building the platform simulator (milestone 5). They are about the platform's rules and the protocol, which the simulator had to follow to the letter. Each says what the simulator does today, so you can see the consequence of your answer before the real platform is built. Questions 16 and 20 were decided on 2026-10-10: each now states the decision, and the simulator follows it.

15. **An abandon that meets a start a worker has just claimed.** The endpoint answers `409 stale_run` with no run, because the run is not written yet. Recommended: the platform inspects at once, closes nothing, and keeps the abandon pending until the start's `expiresAt` plus 300 seconds, abandoning the run with the attempt shown as soon as a snapshot shows it. The cost: an operator can wait up to 65 minutes for the final word. If no: the request ends at the first inspect, and a run that appears afterwards is open again with the abandon forgotten, which is what the simulator does today. Appendix A and rule 7 of appendix B say different things about this case until you choose.

16. **The definition name in every snapshot.** Decided on 2026-10-10. The `run` object of every report, of every `inspect` answer and of every `abandon` answer carries a field `definition`: the tag of the run when the tag has the form of a definition name, otherwise null. It is null for a run with no tag, and for a run that code outside the SDK started with a label of another form. The platform adopts a run it sees only in a snapshot under that definition when the manifest holds it, so that it can wake it. That is the case when both notices of a run your code started are lost: without the field such a run was sent nothing, and its timer did not fire. The platform also compares the definition before it sends a wake, an `inspect` or an `abandon` (appendix B, rule 3). The cost: one field in three messages. For a run the SDK started nothing new leaves the application, because definition names already cross. A tag that code outside the SDK set crosses too when it has the form of a definition name (section 1).

17. **The order of two snapshots.** `at` is in whole seconds, and two hosts of one application can differ by a few seconds. Recommended for protocol 1: keep whole seconds; on a tie the platform closes nothing and inspects one second later, as rule 7 now reads. The cost: one more request per tie, and no protection against clocks that differ: a snapshot that shows no run, taken by a host a few seconds ahead, can close a run another host started a moment later, and if that run sleeps on a timer nothing opens it again. The real fix is a counter kept with the run in the store and raised at every write, which needs a change in Neuron's core. If you want the gap closed before that, rule 7 needs a margin, or an inspect before a run is closed on a difference of a few seconds.

18. **A sync that waits for an owner to confirm an endpoint move** (appendix B, rule 16). Recommended: a new final code for a sync, `endpoint_unconfirmed`, answered `409`, so that the deploy fails with a message that says what a person must do. The cost: one code in the protocol and in the `Code` enum. If no: `422 endpoint_unverified`, which blames a ping that never happened. That is the simulator today.

19. **When the count of the retry policy starts again** (appendix B, rule 9). Recommended: when a segment of the run ends without failing, so that the policy counts failures in a row, as `$tries` did for each job. If no: failures count over the whole life of a run, and a long run that fails once at each of four steps exhausts a policy of 3 although every retry worked. That is the simulator today.

20. **What follows the last re-send of an order.** Decided on 2026-10-10. The delivery values are in the Durations table of appendix B: a back-off of 5 seconds doubling to 300 before a message is sent again; 5 re-sends after a `500`, a `3xx` or a timeout; a ping every 60 seconds after a `401` until one succeeds; a `Retry-After` holds back every message to that endpoint. After the last re-send of a start or a wake the platform does not end it. It alerts, and treats the message as accepted and silent: rule 10 then asks about a wake after the wake silence and sends it again when the attempt is unchanged, and rule 12 asks about a start after its use-by time (appendix B, rule 13). An `inspect` or an `abandon` that exhausts its re-sends is sent again at a slow pace and is not forgotten. The reason is a loss measured on the simulator, which ended the order with an alert until then: an application endpoint that could not be reached for 155 seconds, as during a deploy or a restart of the web tier, lost the wake of every timer that came due in that time, for good. Now such an endpoint never loses a timer: the wake leaves once the endpoint answers again.

21. **Which report answers which announcement when a wake is sent again.** The `invocationId` of a platform message is the same on every re-send, so two copies of one wake can each post an announcement and a report under one ID. Recommended: a new `invocationId` for every wake the platform decides again (after "too early", after the inspect that follows silence), and the same one only when the same message is sent again because its delivery failed. No change to the protocol. If no: the platform pairs them by `at`, as the simulator does today, and can take the report of a first copy for the report of a second copy whose worker died, so that nobody asks about that segment.

22. **A start your code dispatched that expires in the queue.** The platform is never told the use-by time of such a start, so rule 12 cannot be applied to it as written. Recommended: no new field. A run of the application known only from reports that name no run is asked about 300 seconds after its last report, and closed as lost when nothing claimed it, as "ended, outcome unknown" otherwise. That is the simulator today, with one precision: it closes the run as lost only when a report also said that the start had expired (`rejected: expired`), because until then an unclaimed run ID does not tell it that no copy can still run. A start of yours that was lost with its job, whose `observed` report shows `claimed` false and no run, is therefore closed as "ended, outcome unknown": the end-to-end tests of the Laravel bridge assert that. If no: `expiresAt` travels in the announcement and in the report of a start, one field in two messages.

Questions 23 to 37 came from building the Laravel bridge of section 10. Questions 23 to 32, 36 and 37 were decided on 2026-10-11 and are applied: each says what was decided, and sections 4, 9 and 10 describe the result. Questions 33, 34 and 35 are open, and each says what the code does today. Question 38, at the end, was decided the same day and is applied too. Question 39 came the same day with two components for tracing and for evaluation results: what you decided is applied, and it lists what is still yours to confirm.

23. **The floor of Laravel 12.** Decided on 2026-10-11: `^12.41 || ^13.0`. Two things hold from there on that did not hold at 12.15, the floor question 14 first gave. From 12.26 Laravel can begin a SQLite transaction with its write lock (`transaction_mode`), which the end-to-end tests of example (b) need, because their processes share one SQLite file. From 12.41 `response()->stream()` no longer flushes an output buffer of PHP that is not open, so the stream of example (b) does not depend on PHP's `output_buffering`. The cost: an application on an older Laravel 12 updates Laravel before it installs the bridge. Asked for the lowest versions the bridge allows, Composer installs 12.69.0 today, because by default it leaves out the releases that carry a security advisory. The end-to-end tests still need PHP 8.4, where Laravel applies `transaction_mode`: on PHP 8.2 and 8.3 the bridge rests on its in-process tests.

24. **The public names of the bridge that section 10 did not give.** Decided on 2026-10-11: they stay as they are, and they are public API. `invocation()` on both jobs returns the message a job carries: a test of an application reads it after `Queue::fake()`. `displayName()` on both jobs is read by Laravel's queue, and `tags()` by a queue dashboard such as Horizon: the display name is the class, the verb and the definition, and the tags are `iq-php`, `verb:…`, `definition:…`, `workflow:…` and `run:…`, all of which already reach the platform. `$backoff` on `Jobs\ObserveRun` is a property Laravel's worker reads. The config file is published with the tag `iq-config`, the two default queue names are `iq-php` and `iq-observe`, and the platform URL is read from `IQ_PLATFORM_URL`. The cost: each is a name that a later release cannot change without breaking a config file, a deploy script, a dashboard filter or a test. The two jobs, the provider and the controller stay open to subclasses, so their protected members (`execute()`, `tryAgainOrFail()`, `tryAgain()` and `iq()` among them) count as surface too.

25. **The line the bridge reports for a try that did not run.** Decided on 2026-10-11: it stays. After `Jobs\RunInvocation` has queued the copy of an invocation that was not dealt with, it hands the application's exception handler an `IQException` that names the verb, the definition, the workflow ID, the run ID, the reason, the class of the cause and the delay, and never the message of the cause. Such an invocation is an aborted start, answer or signal of yours, or any segment in a worker with no API key. `Jobs\ObserveRun` reports a line of the same form for each try of a notice in a worker with no API key, and for no other reason. A job that queues a copy ends normally and fires no event, so nothing else tells you that a start your code dispatched has not run yet, for up to an hour (24 hours for an answer or a signal). The cost: one error line for each job and try, in the application's log and in its error tracker. A deploy that leaves workers on the old code writes one for every start, answer or signal of yours on a new version that they take, at each of its tries. The same handler receives an exception that a listener of `InvocationSettled` throws, whole and with its message: it is the application's own exception, reported by the application's own handler.

26. **A job that changes a PHP setting while it runs.** Decided on 2026-10-11: it stays. `Jobs\RunInvocation` sets `zend.exception_ignore_args` to 1 before it calls `invoke()` and gives the old value back when it ends. Laravel builds the exception of a job timeout inside the signal handler, on the stack of the code it interrupts, and stores its trace with the failed job. With the setting off, which is PHP's built-in value, that trace holds the arguments of the tool call it interrupted. The cost: a library changes a setting of the worker process for the length of a job, and no exception built in that time shows its arguments, in the application's log or in an error tracker.

27. **What the endpoint answers when `IQ` cannot be built.** Decided on 2026-10-11: `503` with the code `unavailable` and a `Retry-After`, as `handle()` answers when the store fails. That is an application with no API key, or with a registration the SDK refuses. The controller builds `IQ` inside a `try`, answers that `503` itself when the build throws an `IQException`, and reports the exception to the application's exception handler at every request. The reason is what the platform does with each status (appendix A). After a `503` it sends the same message again once `Retry-After` has passed, a start until its use-by time, and holds back every other message to the endpoint, so nothing it sent while the key was missing is lost. After the `500` of Laravel's own page it would send the message again 5 times, then alert and treat a start or a wake as accepted and silent. The cost: the controller no longer only hands the request to the SDK, the bridge writes one answer of the protocol itself, and that answer comes before the signature is looked at. `iq:sync` fails for the same causes, so a deploy shows them. What the jobs do in the same state is question 37.

Questions 28 to 32 each asked for an addition to the SDK that the bridge showed a need for. All five are built: section 4 has them.

28. **A factory for the observe of a segment.** Decided on 2026-10-11 and built: `Invocation::observeOf(Invocation $segment): self`. `failed()` of the Laravel bridge queues what it returns, the SDK itself builds the observe of a stream its consumer stopped with it, and a worker written by hand has it for a job its queue gave up. It throws `invalid_request` for an announcement or an observe, which is no segment. The Symfony bridge will use it for the same case.

29. **The registrations with their leases.** Decided on 2026-10-11 and built: `IQ::definitions(): array` returns what was registered, name => [version => lease in seconds]. The sync command of the Laravel bridge prints the leases from it, also those of a definition registered in a provider, and the bridge binds `IQ` itself: its internal subclass is gone.

30. **A public way to turn a `Report` into an array.** Decided on 2026-10-11 and built: `Report::toArray()` is public. The shape it returns is the report of appendix A, which is now API of the SDK. The listener of example (b) stores its reports with it.

31. **The `Report` of an observe the platform did not record.** Decided on 2026-10-11 and built, because nothing local should wait for the platform (section 7, row 6). The `IQException` that `invoke()` throws for an observe the platform did not record, or refused for good, carries the `Report` that was built, in `$report`. `Jobs\ObserveRun` fires `InvocationSettled` for a job that died at the first try whose report read the store, and goes on trying the notice in a job that fires no event. A report that could not read the store shows nothing, so it tells no listener: a later try does. The cost: an event that says what the store shows before the platform knows it, and that fires again when a person replays a notice the platform had refused for good.

32. **The exception of a failed segment, given to the worker.** Decided on 2026-10-11 and built. `Report::$exception` holds what a failed call threw, and what aborted a call, in the process that executed it. It is no field of the protocol: `toArray()` leaves it out, a report encoded as JSON is `toArray()` and nothing more, and a report that is serialized comes back without it, so a queued listener, a cache or a log line that takes the report cannot carry it out of the process. For that, `Report` implements `JsonSerializable`, which this question did not name: confirm it with the property. `Jobs\RunInvocation` hands the exception to the application's exception handler before it fires the event. The handler treats it as the exception of any job, by its own rules: what it is told not to report it does not log. The same is done for an invocation of the platform that an exception of yours aborted. A handler that throws in its turn, as when its log cannot be written, does not fail the job: what it throws would be stored with the failed job, and it can hold the message of the exception it was given. The cost: a `Report` that holds an exception of the application, with its message and its trace, travels in `InvocationSettled` to the listeners of the same process. The name of the property was not in this question: confirm `$exception`, or name it. One difference stays, by question 25: an aborted try of an invocation of yours, which `invoke()` throws for, is reported with the class of its cause and not with the cause itself.

Questions 33 and 34 each ask for a change that is not built. Question 33 has a form that changes the SDK and the protocol, and one that changes the bridge alone.

33. **What an `observed` report of an answer or a signal cannot say.** When the job of an answer or a signal of yours dies, its `observed` report shows the run as the store holds it. A run that is still suspended means either that the segment never ran or that it ran to a new wait, and the listener cannot tell. When it never ran, the message is lost with its job although the caller was told it was queued (section 6). There are two forms, and they can be combined. The report of an observe carries the attempt its segment was fenced with, so that a listener and the platform compare it with the attempt of the run: one field in the body of an observe and in the report, which is a change of protocol 1. Everything else is internal, with protected members: all of `NeuronCore\IQ\Runtime\`, and under `NeuronCore\IQ\Observability\` the classes `Trace` and `TraceExporter` and the constructor of `IQListener`, which takes the internal `TraceExporter`.

- **A registration is a name, a closure, a version and a lease.** One `register()` call per version; the highest is current. There is no definition class to write.
- **The factory receives the workflow ID and the run ID** (null when the SDK reads a snapshot, and when the endpoint abandons a run). PHP ignores arguments a closure does not declare, so `fn () => new OrderWorkflow()` is valid. The SDK calls `for($workflowId)` itself.
- **Local calls throw what Neuron throws**: `WorkflowRefusedException` (and its two subclasses), `InputTranslationException`, a plain `WorkflowException` for an answer or a signal payload that is not JSON-compatible, or the node's own exception. `IQException` covers only what Neuron cannot say.
- **`workflow()` checks what it is given and reads no store.** It throws an `IQException`: `not_configured` before `setPersistence()`, `unknown_definition` for a name that is not registered in this process, and `invalid_request` for a workflow ID outside Neuron's rule. Neuron refuses such an ID itself, but for a start run in place only after the segment was announced. The handle uses the persistence and the dispatcher that are set when it is called, so call `setPersistence()` and `setDispatcher()` first.
- **`handle()` takes the headers in either shape**: name => value, as `getallheaders()` gives them, or name => list of values, as a framework does. Names are read in any case, and of two names that differ only in case the first is read. The values of a list are joined with a space, so each signature is tried. A value that is not a string is ignored, and `$_SERVER` keys are not read.
- **`configure()` applies to the segments prepared after it**, and a second call replaces the first. `run()` and `events()` apply it just before the announcement. `dispatch()` and `recover()` never do: a dispatched segment is built by the factory in a worker, and the wake of `recover()` delivers where the class's own hooks say. The persistence, the lease and the completion policy of 9.1 stay the SDK's: they are imposed again after the callback.
- **A `PendingSegment` is used once.** A second `run()`, `events()` or `dispatch()` on the same object, or on a copy of it, throws an `IQException` (`segment_used`): it would execute the same run ID again. `events()` uses the segment when it is called, also when the generator it returns is never iterated. The first use counts whatever it threw (`dispatch_failed`, `RunInFlightException`, the exception of a `configure()` closure), and whatever the generator of `events()` throws afterwards: Neuron's refusal is thrown by its first iteration, not by `events()`. An answer or a signal prepared again carries the same fence, so a copy the queue took after all is refused as stale. A start prepared again is a new run under a new run ID.
- **With no dispatcher set, every message runs in place.** That is for scripts and tests. A notice that cannot be posted in place counts as a dispatcher that threw, so an unreachable platform then fails `run()`, `events()` and `recover()` before anything executes. The report of a segment streamed with `events()` is then posted by the process that streams, when the stream ends or its consumer stops. `dispatch()` executes the whole segment before it returns, and returns the run ID also when a node threw.
- **`register()` checks what it is given.** It throws an `IQException` (`invalid_request`) for a name or a version the protocol cannot carry and for a lease under 1 second. A second call with the same name and version replaces the first.
- **`definitions()` lists what `register()` was given**: every name, with the lease of each of its versions. It is the list a sync publishes, and a sync command prints the leases from it. A name made of digits alone comes back as an integer key, as in any PHP array.
- **`setEndpointUrl()` names the URL the platform calls**, once, in the bootstrap. `sync()` publishes it when it is given no URL, and the endpoint answers it when the platform asks for a sync (9.4). It is checked when a sync uses it, not when it is set: in the Laravel bridge `IQ` is built for every request of the platform, and a build that threw would be answered `503` to every message (question 27). A URL given to `sync()` is published instead of it. `sync()` with neither throws `not_configured`, before anything is sent.
- **`Invocation::observeOf()` builds the observe of a segment whose job the queue gave up.** A worker calls it when its queue tells it that the job of a segment died or was kept aside. The observe names the segment and says nothing of how it ended, so the report a worker posts for it says `observed` (9.8). It throws an `IQException` (`invalid_request`) for an announcement or an observe, which is no segment.
- **A `Report` holds what the call threw, in the process that executed it.** `$exception` is set on the report `invoke()` returns for a segment that failed and for a call that an exception aborted, so that a worker can hand it to its error handler. It is no field of the protocol and never leaves the process by the report's own doing: `toArray()` leaves it out, a report encoded as JSON is `toArray()` and nothing more, and a report that is serialized, as in a queue or a cache, comes back without it. That matters because an exception can show more than its message: the HTTP exception of a provider has its request and its response as public properties, with the key of the provider and the prompt in them. The report an observe posts later, in another process, has the class in `$errorClass` and no exception. Where PHP keeps the arguments of a stack trace (`zend.exception_ignore_args` off, its built-in value), the exception holds the workflow that executed, and with it the store connection of that workflow: both live as long as the report, and no longer. The SDK keeps nothing else that holds the exception.
- **`toArray()` is the report of appendix A.** An application that logs or stores a report uses it.
- **The exception of an observe the platform did not record carries the report.** `invoke()` then throws `report_undelivered`, or the reason of a final refusal, with the `Report` that was built in `$report`: what the store shows does not wait for the platform. Every other `IQException` has none.
- **`enableTracing()` is off until it is called, and is called before `workflow()` and `tracer()`**, like `setPersistence()`. From then on every segment the SDK executes in this process is traced, wherever it runs: in a request, in a job, as a stream. An agent or a workflow the application runs itself is traced once it subscribes a listener from `tracer()`. 9.9 says what a trace holds. `$captureContent` false keeps prompts, completions, tool arguments and tool results in your application; the message and the stack trace of an exception are sent either way.
- **`tracer()` returns a new listener at every call, for an agent or a workflow the application runs itself** with `chat()`, `stream()`, `run()` or `events()`: `$agent->subscribe(ObservabilityEvent::class, $iq->tracer())`. The listener takes the settings `enableTracing()` was given, read when `tracer()` is called, and names its spans after the class of the agent or the workflow. One got before `enableTracing()` was called handles no event, so a line that subscribes it sends nothing where tracing is off. The line asks for the service, which needs the key: where the key may be missing, the application asks for the service only when tracing is on, as the guarded entries of the README and the skills do (question 42). It needs the API key and nothing else: no persistence, no dispatcher, no registered definition. One listener keeps apart the runs it hears, so it may serve several agents, and it leaves a run the SDK executes to the SDK (9.9). Its one public member is `__invoke()`.
- **`evaluationOutput()` needs the API key and nothing else**: no persistence, no dispatcher, no registered definition. `evaluation.php` is plain PHP, so it builds the service, or takes it from your container, and lists the output beside its own. `$environment` names where the evaluation ran, such as `ci`.
- **`dataset()` needs the API key and nothing else, and reads nothing when it is called.** An evaluator receives `IQ` in its constructor and returns `$this->iq->dataset('refund-requests')` from `getDataset()`. Neuron's evaluation command builds every evaluator through its resolver, so the resolver is the application's container: the `neuron:evaluate` command of the Laravel guide, or the `resolver` entry of `evaluation.php`. Without a container, `evaluation.php` builds the service and its resolver hands it over. `load()` throws an `IQException` when the items cannot be read (9.9).
- **`FakePlatform` stands in for the platform of every stage.** A test gives it to `IQ` as its HTTP client. `assertTraced()` and `assertEvaluated()` look at the traces and the evaluation results it took in, and `keepDataset()` makes it answer the read of a dataset with the items it is given, so a test of tracing or of evaluation needs no subclass of it (appendix C).
- **The workflow must extend `NeuronAI\Workflow\Workflow`**, because the setters the SDK needs are on the concrete class, not on `WorkflowInterface`.

```php
$response = $iq->handle($_SERVER['REQUEST_METHOD'], getallheaders(), file_get_contents('php://input'));
http_response_code($response->statusCode);
foreach ($response->headers as $name => $value) { header("{$name}: {$value}"); }
echo $response->body;

// bin/worker.php: one message, one call
while ([, $job] = $redis->blPop(['iq'], 0)) {
    $invocation = Invocation::fromArray(json_decode($job, true));
    try {
        $iq->invoke($invocation);
    } catch (IQException $e) {
        $final = in_array($e->reason, [Code::Unauthorized, Code::InvalidRequest, Code::UnsupportedProtocol], true);
        $spent = $e->reason !== Code::ReportUndelivered && $invocation->expiresAt !== null && time() >= $invocation->expiresAt;
        $redis->rPush($final || $spent ? 'iq:failed' : 'iq:later', $job);
    }
}

// bin/sync.php: the last step of a deploy. The endpoint answers the same body when the platform asks for a sync
$iq->sync();

// checkout: start locally, on the queue...
$iq->workflow('order-fulfilment', "order:{$orderId}")->start(new OrderPlaced($orderId))->dispatch();
// ...or run the first segment in this process
$state = $iq->workflow('order-fulfilment', "order:{$orderId}")->start(new OrderPlaced($orderId))->run();

// payment webhook: answer the wait locally
try {
    $iq->workflow('order-fulfilment', "order:{$orderId}")->signal('payment.received', ['amount' => $amount])->dispatch();
} catch (InputTranslationException|WorkflowRefusedException) {
    http_response_code(409);                         // the run is not at that wait: the sender retries
}
```

Run `bin/worker.php` under a process supervisor, one process per concurrent segment. A cron moves the `later` list back every minute, which simplifies the delays of 9.5. A real worker also reads the `Report` that `invoke()` returns and logs a start of your own that did not run (`rejected`, `refused`, or `aborted` after its claim): nothing else in plain PHP tells you, although `dispatch()` returned its run ID. The `failed` list holds what the platform refused for good, which a person replays after fixing the key or the URL, and invocations of your own that passed their use-by time. Section 9.5 says which `IQException` means which.

### (b) Laravel: a chat agent with tool approval

`SupportAgent` is the agent of the Laravel guide. This is the guide's own streaming endpoint with the SDK in place of the direct agent calls: eight lines change, and the agent gains two hooks. The repository of the Laravel bridge holds this example as a real application under `example/`, with a scripted model and a channel that writes to a file, and its end-to-end tests run it on a real queue.

```php
// config/iq.php, with IQ_API_KEY and IQ_SIGNING_KEY in .env
'definitions' => ['support-agent' => App\Neuron\Agents\SupportAgent::class],

public function stream(RunAgentRequest $request, IQ $iq): StreamedResponse
{
    $threadId = $request->threadId();
    Cache::forget(SupportAgent::stopKey($threadId));

    $thread = $iq->workflow('support-agent', $threadId);
    $thread->recover();                                   // replaces the guide's recoverFailedTurn()

    $adapter = new AGUIAdapter(threadId: $threadId, runId: $request->input('runId'), messages: $request->input('messages'), state: $request->array('state'));
    $thread->configure(fn (SupportAgent $agent) => $agent
        ->setStreamAdapter(fn (): AGUIAdapter => $adapter)
        ->setChannel(fn () => null)                       // this segment streams in the response, not on the channel
        ->addFrontendTools($request->frontendTools()));

    $events = $request->isContinuation()
        ? $thread->submitInputs($request->all(), new AGUIInputTranslator)->events()
        : $thread->start(new UserMessage($request->prompt()), stream: true)->events();

    $events->valid();                                     // admit now: a refusal is an HTTP status, not a frame

    return response()->stream(function () use ($events, $adapter): Generator {
        try {
            yield from SSEEncoder::encode($events);
        } catch (Throwable $e) {
            report($e);
            foreach ($adapter->error($e) as $event) {
                yield SSEEncoder::frame($event);
            }
        }
    }, 200, $adapter->getHeaders());
}
```

- **Refusals.** `submitInputs()` throws `InputTranslationException` itself, before anything is announced, when no run is suspended on a wait or the translator refuses the payload. `$events->valid()` throws Neuron's refusal: `RunInFlightException` for a message sent while a run holds the thread, and `WorkflowRefusedException` (`stale_run` or `stale_attempt`) for a continuation that lost a race with another request. The mapping the guide already puts in `bootstrap/app.php` renders them: `InputTranslationException` as 400, `RunInFlightException` and any other `WorkflowRefusedException` as 409. Add a renderer there for `IQException`: 503 for `dispatch_failed` (your queue did not take an announcement) and for `unknown_version` (this process runs older code than the run was started on); the other reasons are programming errors. `recover()`, which the controller calls first, throws both of those reasons too, and `submitInputs()` the second. Laravel logs that `IQException` with the exception before it. For `dispatch_failed` on the database queue that is a `QueryException` whose message holds the whole `insert` statement, the job included: what the job carries is in the log only as the encrypted string of section 10.
- **After `recover()`.** When an approved tool had failed, `recover()` does not run it again: Neuron runs a tool call at most once, because a throw does not prove the effect did not land, and answers the call that threw as interrupted ("it may or may not have taken effect"). An approved call of the same turn that had not started yet runs then. The model ends the turn, with its output going where the agent's own hooks say and not to this response. The `submitInputs()` that follows in the same request then finds no wait and throws `InputTranslationException`, which the mapping renders as 400: a rejection sent after the approved tool failed is answered 400 too, and the tool does not run. Calling the tool again is the model's choice, and a new call, which waits for a new approval. When `recover()` continues a turn the browser had left and that turn stops at an approval, the request for the approval goes to the agent's channel only, and a message the same request carries is refused with `RunInFlightException`. How a chat client should treat these is for the guides to settle, with question 7.
- **Background segments.** An approval that should continue in the background is one call: `$thread->submitInputs($decisions, new ApprovalTranslator())->dispatch()`. A background segment (a dispatched approval, a wake from the platform) is built by the factory in a worker, with no browser request. `SupportAgent` therefore declares what the guide's job used to set: a `streamAdapter()` hook and a `channel()` hook that name the destination from the thread ID.
- **What a background segment does not have.** The AG-UI seed (`runId`, `messages`, `state`) and the browser's frontend tools come from the browser's request. A turn that needs either runs its continuation in the request with `events()`, not with `dispatch()`, and a platform retry of such a turn runs without them.
- **A chat turn needs no `AgentStartEvent` in application code**: `start()` fills the agent's own start event with the messages. Only a structured-output turn builds one (section 3).

### What you must guarantee

1. **The factory rebuilds the workflow from the workflow ID alone.** A worker has no request and no logged-in user. A platform-started agent builds its prompt in its own `startEvent()` hook.
2. **One store and one serializer, shared by every process and by all versions of a definition**, with workflow IDs unique across the definitions that share it. For agents, a durable message store. The SDK's persistence and lease replace whatever the class declares. The persistence factory returns a store on a connection that is still open: a `DatabasePersistence` keeps the PDO it is given, and a worker outlives a database connection (section 10 says how on Laravel).
3. **Per-run input goes in the start event**, never in a state seed. Side effects live inside `memoize()`, and tools are idempotent: the node in flight when a worker dies runs again.
4. **The lease exceeds the slowest node.** The job timeout exceeds the longest segment. The queue's `retry_after` or `redeliver_timeout` exceeds the job timeout. No database transaction is open around a segment.
5. **Every start and answer of a registered workflow goes through `$iq->workflow()`.** A direct `chat()` or `run()` is not announced, so the platform never fires its timers or retries it, and an agent's direct `chat()` silently replaces a failed or dead run that the SDK would have refused to replace. Abandoning a run and resetting a conversation are the exception: use Neuron's own `abandon()` and `resetConversation()`.
6. **The user is authorized for the workflow ID before the SDK is called.**
7. **The queue is durable and as trusted as your code.** It carries the SDK's announcements and reports, and a queued start, answer or signal holds serialized PHP: whoever can write to the queue can run code in the workers and answer any wait.
8. **A breaking change gets a new version**: renaming or moving a node class, renaming or reshaping an event, state or request class, or changing the order of waits or the memo names in a node where a run can be suspended. The old class stays registered until `sync` lists it as retirable. A definition also keeps its name while one of its runs is open, because a run is reached only under the name that started it (9.3): a class registered under a new name leaves those runs to the old name, which stays registered until they have ended. Once the old name is gone, the platform's messages for them are answered `404`, and `submitInputs()`, `signal()` and `recover()` under the new name throw `wrong_definition`.
9. **An event sent before its wait is the workflow's job to look up.** `signal()` refuses when the run is not at that wait; nothing buffers the event.

The SDK checks four of these for you and fails the deploy: the persistence class, a queue that would run in the request, `retry_after` against the job timeout (Laravel), and a bus that wraps the handler in a transaction (Symfony). The rest it cannot see.

Runs that were started before the migration keep working: a run ID the SDK did not mint is handled on the lowest registered version. One exception: a completion the old code retained with `retainCompletionUntilAcknowledged()` and had not acknowledged. The SDK never acknowledges, so acknowledge such runs with the old code before the first SDK call. ## 6. Costs and limits to accept

- **Your queue becomes part of every local segment.** A segment run in a request puts two messages on your queue, also when the platform is healthy, and fails with an `IQException` before anything runs when the queue is down. A start that Neuron refuses in the request, such as a chat message sent while an approval is pending, puts them there too: an announcement, and an observe that says `refused: run_in_flight`, for a run ID that never ran. The platform hears of that run only through those two messages. If both are lost, a run the platform has never seen stays unknown to it until a snapshot shows it: the snapshot in a report about another run of that workflow ID, or the answer to an `inspect` or an `abandon` of that workflow ID. A snapshot shows the definition that started the run, so the platform adopts the run under that definition and wakes it like any other (appendix B, rule 3). Until then its timer does not fire, and while the platform holds no open run on that workflow ID nothing makes it ask. A run with no tag shows no definition: its timer can fire only after an announcement or a report of that run has arrived.
- **A queued start runs once or not at all.** It does not run when its worker dies between the claim and Neuron's first write, when the store fails at that write, when the store commits the claim and loses the answer, or when the job waits in the queue longer than its use-by time (one hour for a start your code dispatched). The queue runs a job once. Before the claim, the platform sends one of its own starts again when a report or an `inspect` shows it unclaimed, and the bridges queue one of yours again after the aborts listed in 9.5; after the claim nothing does. A start of yours whose job is killed or lost is not queued again at all, even unclaimed. Neither is an answer or a signal of yours: when its job is killed or lost before Neuron admitted it, the run stays at its wait although the caller was told the message was queued (question 33). On Laravel the message is still in the failed job: `queue:retry` replays it, and a copy that comes too late is refused by its fence. A platform start that did not run is shown to an operator. One of yours is gone although `dispatch()` returned its run ID: `InvocationSettled` tells you when a report exists. No report exists when the job that would have made it is lost too. Laravel deletes a job before it calls `failed()`, so a worker that dies there leaves no job, no failed job and no observe, and the platform was never told of a start that had not been announced yet (question 34). With the guides' queue retries it would have run.
- **"Lost" and "finished without a report" can look the same.** A start that died between the claim and Neuron's first write, and a run that completed in a worker that died before reporting, both leave no run and a claimed run ID. The platform shows "ended, outcome unknown" and a person decides. Only an unclaimed run ID means "never ran", and only for a start that travelled through a queue: a start run in the calling process is never claimed.
- **A wrong or revoked API key stops nothing when a dispatcher is set.** Runs execute, every announcement and report ends as a failed job, and no timer or retry fires for those runs until the key is fixed and the jobs are replayed.
- **One small record per workflow ID stays in your store.** A ledger entry is about 50 bytes and is dropped by the next claim on that workflow ID once it is an hour past its use-by time. The record itself is never removed by the SDK: about 260 characters per workflow ID on SQL, for every workflow ID that was ever started through a queue or abandoned by the platform. The persistence interface cannot list or expire records, so cleaning up is a statement the guide will give: on SQL, rows of that partition prefix not updated for a day; on Redis, a key scan of the same prefix; on Eloquent it needs the model's timestamps. Never delete a younger record, and never let the store evict keys: a ledger record that disappears lets a late copy of its start run again.
- **The signing key alone can start runs** (question 12). On a run that carries a tag it acts only through the definition that started the run. A run with no tag is not checked: there the key still acts through whichever registered definition a message names, and an abandon that names another definition skips the guard of an Agent.
- **The ledger uses a partition name that begins with `__`.** It relies on Neuron continuing to refuse such workflow IDs.
- **Clocks.** Your hosts must agree with each other within a few seconds. A lease is written with one host's clock and judged with another's, so a difference of D seconds shortens every lease by D, and a lease that ends early lets a second worker take a live run. That is true of Neuron today. Under the SDK it shows sooner, because the platform wakes a run as soon as its lease has passed instead of waiting for the next user message.
- **`FilePersistence` and `InMemoryPersistence` are refused.** Their conditional writes do not hold across processes.
- **Two calls to the platform per segment run in a job** (announcement and report, 3 seconds each at most): a slow platform adds up to 6 seconds to a job, never to a web request.
- **With tracing on, one more call per segment, in whichever process executed it.** The trace is posted when the segment ends, with 3 seconds at most, also in a web request: a slow platform then adds up to 3 seconds to the end of a request, after the last frame of a stream was given. A trace the platform did not take is logged with `error_log()` and dropped: it is never sent again, and a wrong API key shows only in that log.
- **With tracing on, what your application works on leaves it** (section 1). Content capture is on unless you turn it off, and the message and the stack trace of an exception are sent either way.
- **Store operations the SDK adds.** A queued or platform start: one read and one conditional write for the claim. A start run in a request: no claim. A dispatched local start: one snapshot read in the request. A wake: one snapshot read before it executes. Every segment: the snapshot read for its report. An observe of a start: one ledger read. An `inspect` with a run ID: one ledger read. An `abandon`: one ledger read, and one conditional write when the run ID was not there, which creates the ledger record of a workflow ID that had none.

## 7. When things go wrong

| # | Failure | What happens | Why the run stays correct |
|---|---|---|---|
| 1 | The same start is delivered twice, by the platform or by the queue | The second copy finds its run ID in the ledger and reports `rejected: already_claimed` | The claim is one atomic write in your store |
| 2 | A copy of a start arrives after its run completed and its records are gone | The same | The ledger outlives the run |
| 3 | A start arrives after its use-by time | `rejected: expired`; nothing is claimed | The time is checked where execution happens, and again at the claim |
| 4 | A wake or an answer is delivered twice | `refused: stale_attempt` with the snapshot, or `stale_run` when the first copy completed the run. | Every admission that executes raises the attempt, and a completed run leaves no record |
| 5 | A report is lost | An observe waits in your queue with the outcome and reports the state as it is then | The outcome was committed before the report was built |
| 6 | The platform is down for an hour | Segments keep running. Announcements and observes pile up on their own queue and drain afterwards. Timers fire late | Nothing local waits for the platform |
| 7 | A worker is killed mid-segment | No report. Laravel's `failed()` queues an observe; on Symfony the listener does so only when the transport gives the message up before the handler runs. Otherwise the platform asks when the lease it was told runs out. It then sends a wake. A start, an answer or a signal of yours that the worker had not yet given to Neuron is lost with its job (section 6) | The lease and conditional writes: committed steps replay, only the node in flight runs again |
| 8 | A slow worker is taken for dead | Its next write is refused, `stale_attempt`. The node it was in has run in both workers, which is why the lease must exceed the slowest node and side effects sit in `memoize()` | Conditional writes |
| 9 | A node throws | `failed`, with the exception class and the snapshot | `failed` is committed before the exception surfaces |
| 10 | The store fails during a commit, or cannot be read for the report | The outcome and the snapshot can disagree: `failed` with a snapshot that says `running`, `suspended` or no run, when a write was committed and its answer lost; `aborted` although the attempt was raised. Or `snapshotRead` is false, and the platform asks | The platform plans from a snapshot that was read, never from the word |
| 11 | A job is accepted and never runs | Silence. The platform asks: a wake is sent again; a start is asked about 300 seconds after its use-by time, too late to be sent again, and closed as lost when unclaimed or as "ended, outcome unknown" when claimed | A `202` promised nothing |
| 12 | A deploy removes or has not yet delivered a version | `404` at the endpoint or `aborted` in an old worker; both are sent again while the version is in the manifest | Runs meet the code they were started on |
| 13 | A timer fires early (clock difference) | Neuron returns the same wait and attempt | Neuron reads its own clock |
| 14 | An event arrives before its wait; an approval is sent twice | `signal()` throws before anything is queued; a second approval prepared before the first one was admitted is `stale_attempt`, or `stale_run` when the first one completed the run; one submitted after that is checked in the request against the wait the run is on then (9.7): `submitInputs()` throws `InputTranslationException` when no run is suspended on a wait, and `WorkflowRefusedException` (`not_awaited`) when the run has moved on to a wait that rejects it, such as a timer | Nothing was written; an accepted answer cannot change |
| 15 | A browser closes a streamed segment | Neuron fails a run it was still executing, and leaves a segment that had already suspended or completed as it is. The observe says `suspended` or `completed` when Neuron had reported that end, and `failed` when the segment had failed and the browser left on an error frame; otherwise it carries no outcome and the report says `observed`, with the snapshot. When PHP itself aborts the request no observe is queued, and the platform asks when the announced lease has passed | The platform plans from the snapshot, and retries a failed run by policy (question 7) |
| 16 | A start meets a run that failed earlier on the same workflow ID | `RunInFlightException` to the caller, in the request | A start never replaces a run. `recover()` is the explicit verb |
| 17 | Wrong signing key, altered body, replayed request | `401`; a replayed start is a duplicate (row 1), a replayed wake is stale (row 4) | Nothing unverified runs |
| 18 | The worker dies between the claim and Neuron's first write | That start never runs. The platform cannot tell it from a run that completed without a report, and shows "ended, outcome unknown"; a local one is lost with its job | The claim is never undone, so nothing can run twice |
| 19 | The API key is wrong or revoked | Segments run. Every announcement and report is answered `401` and ends as a failed job that can be replayed | The store is untouched; the platform catches up from the replayed observes |

## 8. Decisions and the alternatives rejected

| Decision | Chosen | Alternative, and why not |
|---|---|---|
| Stopping a repeated start | A ledger in your own store | Asking the platform before every start, with the platform remembering finished runs. The first merged design did this; its review found three ways to run a workflow twice in those rules, and it made the platform part of correctness |
| Completion retention | Off | Keeping a completed run until it is acknowledged. With the ledger its only remaining use is to survive a worker dying right after its last write; it costs a release step, a rule for who releases what, and chat threads that can be held |
| Undoing a claim | Never | Undoing it when nothing seems to have run. When the store commits a write and loses the answer, "nothing ran" is wrong and the start runs twice (reproduced) |
| Replacing a lost start | An operator, or the next firing | The platform inferring "it never ran" from an empty answer. Two ways to be wrong were reproduced (a ledger entry already dropped; a worker clock behind) |
| Platform calls from a web request | None; the queue carries them | A direct call with a 3 second timeout: up to 6 seconds added to a chat message whenever the platform is slow |
| Payloads | Only coordination data crosses, in both directions | A start input passed through the platform needs a hydrator, a validator and payload storage there. Reserved as the field `input` |
| Events | Your application routes them with `signal()` and `submitInputs()`, checked against the current wait, never buffered | A platform event bus needs payload storage and a meaning for "sent before the wait", which Neuron does not have |
| A start on a workflow ID held by a failed or dead run | Refused; `recover()` is explicit | Finishing the old run inside `start()` is right for a chat turn and a double execution for `order:123` |
| Who owns retries | The platform, with a fenced wake | Queue retries re-send a fence the first attempt already consumed |
| Versions | An integer per `register()` call, carried at the front of the run ID (`2-…`) | A version hashed from the code, as DBOS does, strands every in-flight run at each deploy. Storing the version with the run is the clean fix and needs a core change, deferred earlier |
| Persistence and lease | Imposed on every workflow the SDK builds | Leaving them to the class lets a plain `Workflow` run on its in-memory default with no lease, unnoticed |
| The definition API | `register(name, closure, version, lease)` | A definition class adds a public type per workflow |
| The root object | `IQ` with an optional `httpClient`, as Neuron's providers name it | `transport: GuzzleTransport::discover()` protected a snippet that neuron-ai 4.1.5 no longer publishes |

## 9. How it works

### 9.1 Building a workflow

Every segment, snapshot and management call builds its workflow the same way:

```php
$workflow = $factory($workflowId, $runId)->for($workflowId)
    ->setPersistence($persistence())
    ->setLeaseTimeout($leaseTimeout)
    ->retainCompletionUntilAcknowledged(false);
```

Neuron takes the lease as an argument of each admission and does not store it with the run, so the SDK sets it every time. The serializer stays the workflow's own, and must be the same for every version of a definition: a local call reads a run through the current version before it knows which version the run is pinned to. `sync()` refuses `InMemoryPersistence` and `FilePersistence` before it publishes anything.

### 9.2 The ledger

Neuron refuses a second copy of a start while the run's records exist. Once the run completes, its records are deleted and Neuron has no memory of it: the same start would run again. The ledger is that memory.

- **Where.** In your store, through the same persistence the workflows use: partition `__iq:` followed by the SHA-256 of the workflow ID, one key `starts`, holding JSON `{"<runId>": <use-by time>, ...}`. Neuron refuses workflow IDs that begin with `__`, so no workflow can collide with it.
- **Which starts.** Every start that travels through a queue or over the wire: one the platform sent, and one your code dispatched. A start executed in the calling process (`run()`, `events()`) exists in one copy and is not entered: its report says `claimed: false` although it ran. Nothing in the SDK queues such a start, and its segment can be used once, so no second copy of it can reach a worker.
- **Claim.** Immediately before a start is given to Neuron, the SDK adds its run ID with one atomic conditional write (`initializeIfAbsent`, or `writeIfUnchanged` on the bytes just read). When another process writes at the same moment it reads again; after five lost tries the start is `aborted: unavailable` and nothing was written. The same write drops entries whose use-by time is more than an hour old.
- **The rule.** A run ID is claimed once and the claim is never undone. A copy that finds its run ID in the ledger does nothing and reports `rejected: already_claimed` with the snapshot.
- **Use-by time.** Every start carries one that the runner enforces (`expiresAt`, at most an hour ahead). The upper bound is checked where a start is created, by the endpoint for a platform start (9.4) and by `dispatch()` for a local one, never by the runner. A start that carries none counts as expired. The runner refuses a start whose time has passed, and the claim refuses it again with the clock read that prunes: a use-by time that has passed means `rejected: expired` and nothing is written. An entry therefore only has to outlive its start by its use-by time, however long a copy is held up between the check and the claim, and the ledger stays small.

### 9.3 The start event

1. No input: the workflow's own `getStartEvent()`.
2. A `Message` or a list of them, for an `Agent` only: a copy of `getStartEvent()`, which must be an `AgentStartEvent`, with the messages set and `stream` taken from the argument. The agent's `startEvent()` hook is respected. `stream` is ignored for any other input.
3. An `Event`: used as given. For an `Agent` its class must be that of `getStartEvent()`.
4. For every workflow that is not an `Agent`, a dry build of the graph proves that a node handles the event: `(clone $workflow)->setStartEvent($event)->export()` throws when none does and touches no store. It proves that some node handles the event, not that the graph begins there: an event a later node handles ignites the run at that node, as in Neuron.
5. An `Agent` started with no messages is refused: it would ignite and then fail on an empty conversation.

A broken rule is `invalid_start`, thrown from `start()` or reported as `rejected` by a job, before anything is claimed or ignited: the event cannot be rebuilt or stored with a run, an agent's event is not of the class of its own, carries no message or carries something that is not a `Message`, or no node handles it. A start event is immutable once a run exists, so a bad one must never create a run.

A hook of the workflow that throws while the event or the graph is built (`startEvent()`, `resources()`, `nodes()`, a node or middleware factory) breaks no rule. `start()` throws it as it is, and a job reports `aborted: not_executed` with its class, like a factory that throws, so the start can be sent again: a store that is down for a moment while `startEvent()` loads the input must not cost the start. That holds for a start the platform sent. For one your code dispatches, the event is resolved in the request and travels in the invocation, so a hook that throws there is thrown to the caller and nothing is queued. One case cannot be told apart: a hook that throws a plain `WorkflowException` during the dry build looks like the graph's own refusal and counts as a broken rule.

Every start the SDK gives Neuron also carries the name of its definition as the run's tag (`ExecutionRequest::start(tag:)`): a start a worker executes, and a start run or streamed in the calling process. Neuron stores the tag with the start record of the run, never reads it and never changes it, and the snapshot shows it. The tag is the name alone: the version stays at the front of the run ID. One rule follows: a run is executed, read for an `inspect` or discarded only through the definition that started it. The SDK compares the tag with the definition a message or a call names in three places, each time on a snapshot it already reads, so no store read is added: before a wake executes (9.5), for an `inspect` and an `abandon` (9.4), and in `submitInputs()`, `signal()` and `recover()` (9.7). A start compares nothing, because a start never replaces a run. A run with no tag is not checked anywhere: it was started outside the SDK, or by a version of the SDK that set none. A run that code outside the SDK started with a tag of its own counts as started by another definition, unless that tag is the name. The platform is shown the tag as the `definition` of the run, in every report and in every answer to an `inspect` or an `abandon`, when it has the form of a definition name; otherwise it is shown null, and a label of another form does not cross (appendix A).

### 9.4 The endpoint: `handle()`

1. A method other than `POST`, compared whatever its case: `405`, before the signature is looked at.
2. Verify the signature over the raw body (appendix A). No key configured, an empty key, a bad signature or a timestamp out of the window: `401`. Nothing is decoded before this.
3. Decode and check the fields of the verb against their formats. Otherwise `400`. For a start that includes a run ID of the minted form and an `expiresAt` no more than 3600 seconds, plus the signature window, ahead. A use-by time that has already passed is not refused here: the start is queued, and the runner reports it `rejected: expired`. A body longer than 65,536 bytes is `invalid_request` and is not decoded; that check comes after the signature, so an unsigned request of any size is still `401`. A body the endpoint cannot decode as a JSON object is `invalid_request`: no JSON, a list or a scalar, text that is not UTF-8, a string with an unpaired surrogate escape, or values nested 512 levels deep, the body counted as the first. An object whose `protocol` is not 1 is `unsupported_protocol`, whatever else it holds. Of two fields with the same name the last one counts. The `invocationId` of a start or a wake that is not the `webhook-id` header is malformed, and an optional field is left out, never sent as null. An `Invocation` is built field by field with `origin` set to `platform`; `payload`, `signal`, `event` and anything else that exists only in your queue are never read from the wire.
4. Look the definition up, and for `start` and `wake` the version in the run ID: `404`. An `inspect` and an `abandon` need only the definition: they read the store through the version the run ID pins when this process has it, otherwise through the current one, whose `abandon()` is then the one called, and are never answered `unknown_version`.
5. `start`, `wake`: hand the invocation to the dispatcher and answer `202`. If the dispatcher throws: `503` with `Retry-After`. No workflow is built and the store is not touched. With no dispatcher set (section 4) the invocation runs in place instead: the segment executes inside `handle()` before the `202`, and what `invoke()` throws there is answered `503 dispatch_failed`. That is for scripts and tests, never for an endpoint the platform calls.
6. `inspect`, `abandon`, `ping`, `sync`: answer in the request (appendix A). A `ping` and a `sync` are answered before step 4: they name no definition. When the run that holds the workflow ID carries a tag that is not the definition the message names, an `inspect` and an `abandon` are answered `400 invalid_request` and nothing is written (9.3): an `abandon` looks at the run before it writes its ledger entry. Anything thrown while the workflow is built or the store is read is answered like a store that cannot be read, whatever threw it: the store, the persistence factory, the application's factory or a hook of the workflow. An `inspect` then answers `snapshotRead` false. An `abandon` answers `503 unavailable` when it happens while the workflow is built, the run ID is claimed in the ledger or the run is discarded, also after the ledger entry was written: the abandon sent again then finds the entry (appendix A).
7. Any other throwable: `500`. Nothing leaves `handle()`, so the application's exception renderers never answer the platform for a request that reached it. A framework can answer before `handle()` is called: section 10 lists what Laravel answers itself.

`handle()` works before `setPersistence()`: a ping, every refusal and, with a dispatcher set, a start and a wake need no store. With no persistence set, an `inspect` is answered `snapshotRead` false and an `abandon` `503 unavailable`, as when the store cannot be read.

A `sync` is the platform asking for the manifest, which an owner can request from the dashboard. The answer is `200` with the body `sync()` would post, built by the same code: the URL of `setEndpointUrl()` and every registered version. Where `sync()` would throw before it sent anything (no endpoint URL set, one that is not `https`, no persistence, an in-memory or file store, no definition, a lease under 60 seconds), the answer is `409 sync_refused` and does not say which: `sync()` does, in the deploy. The store factory is called, to see the kind of store, and no store operation is made; a factory that throws is answered `500`, like anything else thrown. The SDK cannot see the URL the request arrived at, so the answer names the one it was given, and the platform compares the two. An SDK that does not know the verb answers `400 invalid_request`, and the platform reads that as "not supported".

### 9.5 The runner: `invoke()` in a queue job

For a **start**:

1. The definition or the version is missing in this process: `aborted` (`unknown_definition`, `unknown_version`). A worker still running old code during a deploy is the usual cause; the invocation can be sent again.
2. The use-by time has passed: `rejected: expired`.
3. Build the workflow (9.1) and the start event (9.3). A broken rule of 9.3: `rejected: invalid_start`. A factory or a hook of the workflow that throws: `aborted: not_executed`.
4. Announce (9.8).
5. Claim the run ID (9.2). The use-by time has passed since step 2: `rejected: expired`. Already there: `rejected: already_claimed`. The store fails, or five tries are lost: `aborted: unavailable`.
6. Call the workflow's own `run(ExecutionRequest::start($event, $runId, recoverFailed: false, tag: $definition))`, so that a class of yours that overrides `run()` is executed through it, and classify the result. The tag is the name of the definition (9.3). The SDK subscribes to the events of the workflow it built and keeps the execution of the first: a segment opened if one fired, and that execution gives the attempt. It also keeps the status of the `WorkflowEnd` event that the workflow reports for itself, which says how Neuron closed the segment; the `WorkflowEnd` of another workflow, passed on by a node that runs one, is not read. A listener of your own that throws on every event of the workflow still hides the segment: a call that throws is then reported `aborted: not_executed` although a node ran, and one that returns is reported with no `executedAttempt`.

| Result | Outcome |
|---|---|
| A state | `completed` or `suspended` |
| `WorkflowRefusedException` | `refused`, with its reason. A `conflict` is tried once more in place when no segment opened. A refusal other than `stale_attempt` that surfaces after a segment opened escaped from a node: it is `failed`, with its class |
| Another throwable, after a segment opened | `failed`, with the exception class, unless Neuron had already reported the end of the segment (below) |
| Another throwable, no segment opened | `aborted: not_executed`. The claim stays, so this start is not sent again. When the store committed Neuron's first write and lost the answer, the snapshot shows the run, and the platform finishes it with a wake once its lease has passed |
| A wake the guard stops before Neuron is asked (below) | `rejected: wrong_definition` when another definition started the run; `refused: stale_run` when no run with that run ID holds the workflow ID; `refused: executing` when the run is `running` with no lease |

What Neuron reported of the segment comes before this table. When it reported the end of the segment as suspended or completed and the call threw afterwards (the stream adapter threw while it built its last frame, or the consumer of a stream threw into that frame), the outcome is `suspended` or `completed`, with no `errorClass`: that is how the segment ended. The caller of `run()` or `events()` still receives the exception; a queue job reports the outcome only.

7. Read a fresh snapshot through a newly built workflow, in its own `try`, and post the report (9.8). When the pinned version is missing in this process the snapshot is read through the current version, because all versions share one store. When the definition is missing no snapshot can be read, and the report says `snapshotRead` false.

`recoverFailed` is always false: a start only ever creates a run, so a repeated start can never become a retry.

For a **wake**, an **answer** and a **signal**: steps 1, 3 (without the event), 4, 6 and 7, with the fence taken from the invocation and never read again at job time:

| Verb | Neuron call |
|---|---|
| `wake` | `ExecutionRequest::resume(null, $runId, $attempt)` |
| `answer` | `ExecutionRequest::resume($payload, $runId, $attempt)` |
| `signal` | `ExecutionRequest::signal($signal, $payload, $runId, $attempt)` |

A failure while one of these requests is built is `aborted: not_executed` with its class, never `rejected`. An answer and a signal are never rejected, and a wake only as `wrong_definition`, by the guard below.

A wake, an answer or a signal that carries no attempt is never executed, because Neuron would read it as "no fence": `invoke()` throws `invalid_request` before anything is posted.

Before a wake executes, as the first part of step 6, the runner reads the snapshot. It first compares the definition the invocation names with the tag of the run that has that run ID (9.3). When the tag is another name the wake is `rejected: wrong_definition`, whatever its attempt: nothing executes, the run is left as it was, and `invoke()` returns the report without throwing, because the wake is final. The report carries the snapshot like any other. The runner then refuses with `executing` when the run with that run ID and attempt is `running` with no lease. That can only be a run started outside the SDK, and a wake would take it over while its process is alive. When that read shows no run with that run ID, the runner refuses the wake as `stale_run` itself and Neuron is not asked: a run that took the workflow ID after the read would be continued with its tag unread. A queued answer or signal is not checked here: it was checked when it was prepared (9.7), and the runner reads no snapshot for it.

`invoke()` returns the `Report` (for an `announce`, one with the outcome `observed`). The report of a segment that failed, and of a call that an exception aborted, holds that exception in `$exception`, in this process only (section 4). It throws `IQException` when the message was not dealt with, and `$e->reason` tells the worker what to do. For an abort, the exception names the definition, the workflow ID and the run ID, and its previous is the throwable that caused it:

| Reason | What the worker does |
|---|---|
| `report_undelivered` | Give the same message to `invoke()` again later (after 10, 30, 60, 300, then every 900 seconds), without limit |
| The code of an abort (`unknown_definition`, `unknown_version`, `not_executed`, `announce_failed`, `unavailable`), for an invocation your own code issued | The same, while `time() < $invocation->expiresAt`; after that time, keep it aside like a final one. A start that was aborted after its claim is not thrown: it cannot run again |
| `unauthorized`, `invalid_request`, `unsupported_protocol` | The platform refused the message for good, or the message cannot be executed as it is (a wake, an answer or a signal without an attempt): keep it aside for a person |

`not_configured` is thrown before the message is looked at, when `setPersistence()` was never called: nothing was done and nothing was reported, and the same message can be given to `invoke()` again once the bootstrap is fixed.

The bridges do this. A worker you write yourself must. A queue that runs a message in the process that queues it, as Laravel's `sync` queue does, has no later try: the Laravel bridge queues no copy there and throws, so that the caller of `dispatch()` is told (section 10).

### 9.6 A segment run inside a web request

`start()->run()`, `start()->events()`, `submitInputs()->run()` and their like execute in the calling process and, with a dispatcher set, make no call to the platform:

1. Check the event and mint the run ID (`<version>-<uuid>`): `start()` does both. `run()` or `events()` then applies the `configure()` closure and hands an announcement to the dispatcher. A closure that throws is thrown as it is and nothing is announced. If the dispatcher throws, the call fails with an `IQException` (`dispatch_failed`) before anything ignites.
2. Execute. A `conflict` on a start is tried once more in place, as in 9.5: Neuron retries it by itself only for a start that reserves no run ID, and the SDK always reserves one. The state is returned, and any other refusal or the node's exception is thrown, as without the SDK.
3. Hand an observe that carries the outcome to the dispatcher. A worker reads the store and reports. If the dispatcher throws here, the state is still returned, or the exception of step 2 still thrown.

With `events()`, all of step 1 happens before the generator is returned: the event check, the `configure()` closure and the announcement. An `IQException` (`segment_used`, `dispatch_failed`) and the exception of the closure are thrown by `events()` itself, before a response has sent anything. `events()` asks Neuron nothing: Neuron admits the segment on the first iteration, as without the SDK, and its refusal is thrown there. Call `valid()` right after `events()`, as example (b) does. A `conflict` on a start is tried once more at that first iteration, as in step 2; Neuron yields nothing before it opens a segment, so the consumer has received nothing of the first try.

The generator yields what Neuron's own `events()` yields, with the same keys and in the same order, returns the state Neuron returns and throws what Neuron throws. An exception the consumer throws into the generator, as Neuron's `SSEEncoder::encode()` does for a frame it cannot encode, is passed to Neuron and is not a stop. While the segment is executing, Neuron fails the run for it, yields the error frames of the stream adapter and throws it back. On a frame Neuron yields after it settled the run (one of the last frames of a segment that suspended or completed, or an error frame), Neuron leaves the run as it is, yields nothing more and throws it back at once. Either way the stream has thrown that exception, and 9.5 says what is reported. Thrown into an error frame, it changes nothing of the report: the segment had failed before, and the observe carries the class of what failed it.

A stream ends in the consumer's hands when Neuron returns the state or throws there. The observe of step 3 is handed to the dispatcher before the consumer receives either, with the outcome 9.5 gives. A consumer that releases the generator before that (it goes out of scope or is unset; a `break` alone releases nothing while a variable still holds it) makes Neuron fail a run it was still executing, and leaves a segment that had already suspended or completed, and was only yielding its last frames, as it is. PHP destroys Neuron's generator before the SDK hands the observe over, so the store already shows what Neuron left.

A segment that fails does not wait for the end of its stream. Neuron marks the run failed in the store, yields the error frames of the stream adapter and only then throws. The observe is handed to the dispatcher when Neuron yields the first of those frames, before the consumer receives it, with the outcome `failed`, the class of what was thrown and the attempt. A consumer may stop on an error frame, and PHP does not always destroy a stream that is left there (question 38). Without a stream adapter Neuron yields no frame for a failure and throws at once: the observe is handed over before the consumer receives the exception, as above.

The observe of a stream says only what is known. When Neuron reports the end of the segment as suspended or completed, the outcome is `suspended` or `completed`, with no `errorClass`, however the stream ended: the consumer stopped on one of the last frames, or threw into it, or the stream adapter threw while it built it (9.5). In every other case of a consumer that stopped, the SDK does not say how the segment ended: the observe carries the segment's `invocationId` and `verb` and no outcome, and the worker reports `observed` with the snapshot (9.8). That is so for a stream stopped while its run was executing: the snapshot shows the run `failed`, and the report carries no `errorClass`. A stream stopped on an error frame is not such a case: its observe was handed over with the first of those frames and says `failed`, with the class.

The SDK learns how Neuron closed the segment from Neuron's `WorkflowEnd` event (step 6 of 9.5). A listener of your own that throws on that event, set by the factory or by `configure()`, hides it from the SDK when Neuron calls it before the SDK's listener, which subscribes last. A stream stopped on one of its last frames is then reported `observed` with the snapshot, and a call that threw after Neuron had closed the segment is reported `failed`, as the table of 9.5 says. A stream taken to its end is not affected.

The SDK learns that a streamed segment failed from Neuron's `WorkflowError` event, which Neuron reports once it has marked the run failed in the store. Neuron reports the same event for a listener that threw, and the segment goes on then. So the SDK reads the run in the store, as `inspect()` does, at each `WorkflowError` the workflow itself reports, and takes the event for the failure only when the store shows this run `failed` at this attempt. It reads nothing for an error reported under a node, nothing once it has found the failure, and nothing for a segment run with `run()`, which yields no frame. A store that does not answer that read changes nothing for the listeners that follow: the stream then tells how the segment ended when it ends. A listener of your own that throws on `WorkflowError` hides the failure from the SDK as one that throws on `WorkflowEnd` hides the end. A stream stopped on an error frame is then reported `observed` with the snapshot, and its observe is handed over when PHP destroys the stream: at once where PHP leaves the arguments out of a stack trace, and otherwise when PHP collects cycles or the request ends (question 38). A stream taken to its end is not affected.

A generator that is never started has used the segment and announced it, asks Neuron nothing and hands no observe: the platform asks when the announced lease has passed (appendix B, rule 10) and finds the store unchanged. Any method of the generator starts it, `getReturn()` included. A process forked while a stream is open holds a copy of the stream. When the child releases its copy without having taken the stream to its end, Neuron settles nothing there and the SDK hands nothing to the dispatcher: the process that took the first step of the stream reports it.

When PHP itself ends the request because the connection was aborted (`ignore_user_abort` off), it runs no `finally` block, so no observe is handed over. Neuron's segment is still destroyed and fails a run it was executing: the store shows `failed` with no lease, and the platform learns it when it asks, `leaseSeconds` after the announcement (appendix B, rule 10). Only a fatal error (a time limit, a memory limit) or a killed process leaves the run `running` under its lease, with the announcement alone in the queue.

`start()->dispatch()` reads the snapshot once, throws `RunInFlightException` when a run holds the workflow ID, and otherwise hands the start to the dispatcher with a use-by time one hour ahead. The job claims it.

### 9.7 Answers, signals and `recover()`

`submitInputs()` and `signal()` check everything in the request that received the answer:

1. Read the snapshot, through the current version: the run ID, and with it the version, is not known before. A run that carries the tag of another definition: an `IQException` (`wrong_definition`), whatever state the run is in, thrown before the version is looked up and before the translator is asked (9.3). No run, or one that is not suspended on a wait: `InputTranslationException`. This is stricter than Neuron's own `submitInputs()`, which checks only that a run exists and that a wait is attached. When a run is `running` or `failed` with its answered wait still attached, Neuron stages the answer and decides at `run()`: `executing` while the run is `running`; on a `failed` run the same answer is accepted and retries the run, and a different one is `not_awaited`.
2. Read the version from the run ID; that version is built once step 3 has accepted the payload. A run ID the SDK did not mint gets the lowest registered version. A version this process lacks is an `IQException` (`unknown_version`), thrown before the translator is asked, also when the segment would only be dispatched to a worker that has it.
3. Translate with the given translator, against the current wait. For a signal, the wait must be a `WaitForEventRequest` with that name, otherwise `WorkflowRefusedException` (`not_awaited`). The wait's own rule is then applied, as Neuron applies it when it admits the answer: an answer or a signal payload the wait rejects, such as any answer for a run that sleeps on a timer, is `WorkflowRefusedException` (`not_awaited`) with the wait's own message, and a payload that is not JSON-compatible is Neuron's plain `WorkflowException`, a programming error the examples of section 5 do not catch. A payload Neuron would refuse is therefore never queued. Nothing has been written.
4. Capture the snapshot's run ID and attempt in the invocation. They are never read again, so a second delivery of the same answer is refused as `stale_attempt` (`stale_run` once the run has completed) and cannot reach a later wait. A dispatched answer or signal also carries an `expiresAt` 24 hours ahead; the runner never checks it, and the bridges use it only to stop queueing an aborted one again.
5. `run()`, `events()` or `dispatch()`.

`recover()` reads the snapshot and, when the run is `failed` or `running` with an expired lease, executes a wake fenced with the attempt just read, in this process. Like `submitInputs()` and `signal()`, it throws `wrong_definition` when the snapshot shows a run that carries the tag of another definition, whatever state that run is in, and executes nothing. It returns the state, or null when there was nothing to do or when someone else got there first (`stale_run`, `stale_attempt`, `executing`), also when its own segment had opened and lost the run to another process while its node was executing. A node that fails again throws, as in Neuron. `recover()` leaves a suspended run alone even when its timer is due, which is the platform's wake, and a run that is `running` with no lease, which was started outside the SDK. It replays the answer a failed or dead run had already accepted. The SDK never calls `recover()` by itself.

### 9.8 Announcements, reports, observes

- **Announcement.** "A segment of run R is starting; its lease is L seconds." A notice, not a question: nothing in the SDK depends on the answer. A job posts it directly (one try, 3 seconds); if that fails, with a final answer or not, it hands it to the dispatcher and continues. If the dispatcher fails too, a segment your code issued is `aborted: announce_failed` before it ignites, and a segment the platform issued continues, because the platform already knows it. A web request only hands it to the dispatcher.
- **Report.** After a segment: the outcome, and a snapshot read from the store just before sending. A job posts it once; on any answer but `200`, a final one included, it hands the dispatcher an observe that carries the outcome, so the later report still says `completed` or `failed`. If the dispatcher throws there, the job still ends normally and `invoke()` returns the report: the platform learns the state when it asks (appendix B, rule 10). When the snapshot could not be read, the report is still posted, with `snapshotRead` false, and no observe follows a report the platform recorded: the platform asks (appendix B, rule 6).
- **Observe.** A worker reads a fresh snapshot and, for a start, the ledger, and posts one report: with the outcome the observe carries, or with `observed` when it carries none (a job that died, or a stream whose consumer stopped, unless Neuron had reported the segment as suspended, completed or failed: 9.6). When the store cannot be read, the report is still posted, with the outcome the observe carries and `snapshotRead` false, and the platform asks. Undelivered, `invoke()` throws `report_undelivered` and the queue retries it with a back-off and without a time limit: from `invoke()` that reason only ever means the platform did not record the message. The exception carries the report that was built, also when the platform refused it for good, so a worker can tell a listener at once what the store shows. A final `4xx` ends it as a failed job that can be replayed, never as a completed one. The bridges keep announcements and observes on their own queue, so that a platform outage cannot delay real segments.

### 9.9 Traces and evaluation results

Neither is part of the durable protocol: a run is correct with both off, and a platform that takes neither in changes nothing for a run.

**Traces.** An `IQListener` hears every event Neuron reports for a segment and turns it into spans: one for the segment, named `invoke_workflow <name>` or, for an agent, `invoke_agent <name>`, and under it one for each node, branch, middleware, inference, tool call, retrieval and structured-output step. They follow the OpenTelemetry conventions for generative AI, so any OTLP backend reads them. Listeners are subscribed in two places. Once `enableTracing()` was called, the build step of 9.1 subscribes one of the SDK's own to every workflow built with a run ID, which is every workflow built to execute; a workflow built to read a snapshot gets none. Its spans are named after the definition. And the application subscribes one that `tracer()` returned to an agent or a workflow it runs itself, and may give one to the workflow the factory of a definition returns: its spans are named after the short name of the class of the run's source. Such a listener takes the settings of `enableTracing()` when `tracer()` is called, and handles no event when `enableTracing()` had not been called by then. In the Laravel bridge a callback of the provider gives every agent and workflow the container builds a listener of its own, which takes one from `tracer()` at the first event it hears, and leaves them untraced, reporting the cause once, when `IQ` cannot be built then (section 10).

- **One listener, several runs.** A listener keeps apart the runs in flight, by the run ID Neuron stamps on every event of a segment (`$event->execution->runId`): for each, its trace, the thread of an agent and its provider. The `WorkflowEnd` of a run sends the trace of that run and forgets it, and leaves the other runs untouched. One listener therefore serves an agent whose tool runs another agent, a node that runs an agent, and two streams read in turns, with a trace for each run. The events that carry no execution share one trace.
- **A run the SDK executes is traced once, by the SDK.** The SDK's listener claims each segment it hears: at the first event it hears of a segment, it enters the execution context Neuron stamps on every event of that segment in a registry of the process, a static `WeakMap` of `IQListener`. The claim lasts as long as Neuron holds the segment, and never reaches the next segment of the run. Any other listener that hears an event of a claimed segment drops what it holds of that run and handles none of its events. A listener the workflow already holds when the factory of a definition returns it, as when the factory takes the workflow from a container that subscribes one (the callback of the Laravel bridge, or a PHP-DI definition), comes before the SDK's: it hears the first event of a segment before the claim and drops what it gathered at the next, and it hears `WorkflowEnd` while the claim stands, so it sends nothing. One that a `configure()` callback subscribed comes after the SDK's and leaves the run alone from its first event. A run whose segment the SDK does not execute is not claimed: an agent that a tool runs inside a segment of the SDK is a run of its own, with its own run ID, and its `tracer()` listener traces it under its class; a later segment of a run the SDK traced, executed outside the SDK, is traced by a listener of the application.
- **One trace per run.** The trace ID is the first 32 hexadecimal characters of the SHA-256 of the run ID. Every segment of a run sends its own spans under that trace ID, each with a parentless span of its own, and every span carries `neuron.run.id`, `neuron.workflow.id` and the attributes given to `enableTracing()`. The parentless span carries `neuron.run.status`: `completed`, `suspended` or `failed`. The parentless span of a segment after the first, one whose `$event->execution->executionAttempt` is above 1, also carries `iq.run.resumed` (`true`), which the platform's protocol defines: the platform counts a run from the parentless span that lacks it. A run whose first segment's trace never reached the platform, because its process died before `WorkflowEnd` or the export failed, therefore counts no run.
- **The status comes from the end of the segment.** Neuron reports `WorkflowError` for the failure of a run and for a listener that threw while the run goes on, so the event alone says nothing: it becomes an `exception` event on the span that was open. The run is `failed` when the state of `WorkflowEnd` says so, and that span then carries the error status, with the class and the message of the last error.
- **What a trace holds.** Always: the names of nodes, tools, models and the provider, token counts, timings, the thread ID of an agent as `gen_ai.conversation.id`, and for every error its class, its message and its stack trace. With content capture, which is on unless `enableTracing(captureContent: false)`: the messages given to and returned by the model, and the arguments and the result of every tool call, each cut at 4,000 characters.
- **When it is sent.** At the `WorkflowEnd` of its run, by the process that executed the segment, as one `POST {platformUrl}/v1/traces` with the timeout of a notice. In a job it goes between the announcement and the report. In a web request it is the only call the request makes to the platform, after the last frame of a stream was given. A stream left on an error frame sends it when PHP destroys the stream (question 38).
- **Best effort.** Any 2xx answer takes the trace in. Anything else, no answer, and a trace JSON cannot carry are logged with `error_log()` and dropped: nothing is thrown, nothing is queued, and the announcement, the report and the outcome of the segment are what they would be without tracing.
- **A segment that fails while it is built is traced too.** Neuron reports no start for it, only the error and the end: the error opens the span of the segment, and the trace says `failed` with one span. A trace with no span is never sent.
- **Your listeners come first.** The SDK's listener is subscribed after those your factory subscribes, and Neuron stops at a listener that throws. One of yours that throws on an event keeps that event from the trace. One that throws on the start of a segment does not hide the segment: Neuron reports what it threw under the workflow, and that report opens the span of the segment. One that throws on `WorkflowEnd` keeps the whole trace of that segment from being sent. `WorkflowEnd` is then not the last event: Neuron reports what any listener threw on it as a `WorkflowError` after it, whether that listener comes before the SDK's or after it, as one of a `configure()` callback does, or is the external dispatcher of `setEventDispatcher()`. A listener that heard the `WorkflowEnd` of a segment handles none of its events after it, and the claim ends with the segment, so the next segment of the run is traced as any other.

**Evaluation results.** `evaluationOutput()` returns an output for Neuron's evaluations. The evaluation command gives every listed output the report of the run when all evaluators are done; this one posts one message per evaluator to `POST {platformUrl}/v1/evaluations`, with 15 seconds each: the evaluator's class and namespace, the environment, when it started and finished, its summary, and for every dataset item its input, its output, its scores and its failed assertions. It is best effort in the same way: a message the platform did not take is logged, the next evaluator is still sent, the outputs listed after it still run, and the exit code of the command is unchanged.

**Datasets.** `dataset()` returns a dataset of Neuron's evaluations whose items the platform keeps. Neuron's runner calls its `load()` once per evaluator, after `setUp()` and before the first item runs, in the process of the command: with `--concurrency` the children receive the items and never read them. `load()` is one `GET {platformUrl}/v1/datasets/{slug}` with the API key and 15 seconds, and returns the `items` of the answer as they are: each is an array, today with the `dataset_item_id` the platform gave it and the `input` and the `expected_output` an operator stored. It is not best effort: without its items an evaluator has nothing to run on, so `load()` throws an `IQException`, `unauthorized` for a `401` or a `403` and `report_undelivered` for a `404`, for no answer and for an answer that holds no list of items. Neuron's command catches it, reports the evaluator with that error and no result, runs the next one, and exits with 1. An empty list is a dataset with no item, and the evaluator runs nothing. The evaluation cache keys an item by its content and its `dataset_item_id`, so an item changed on the platform or imported again runs again under `--cache`.

One the `extend()` also runs would ask for `IQ` at its first event while it is still being built: a flag the hook sets while a listener asks leaves it untraced instead (question 42). While tracing is on, an agent the container built holds a closure and cannot be serialized. The provider also binds `Evaluation\IQOutput`, not shared, to `evaluationOutput()` of that `IQ` with the `evaluation.environment` of the config: an `evaluation.php` lists the class and the container, which is the resolver of the evaluation command on Laravel, builds it once the evaluators have run. Without an API key that build throws `not_configured`, and Neuron's command then prints no output at all: the README has `evaluation.php` list the class only where the key is set |
| Config keys | Eleven keys. The three credentials are `api_key`, `signing_key` and `platform_url`, read from `IQ_API_KEY`, `IQ_SIGNING_KEY` and `IQ_PLATFORM_URL`. Two more hold what is optional, and three of their values read the environment too: `tracing` (`enabled`, false, from `IQ_TRACING`, which turns on the traces of the segments the SDK executes and of the agents and workflows the container builds. The provider's callback reads it at each build to decide whether to subscribe a listener, and that listener takes the tracing settings of the `IQ` singleton, fixed when the provider first builds it: a value turned on after that subscribes listeners that send nothing (question 42); `capture_content`, true, from `IQ_TRACING_CAPTURE_CONTENT`; `attributes`, an empty list) and `evaluation` (`environment`, null, from `IQ_EVALUATION_ENVIRONMENT`). `mergeConfigFrom()` fills only the first level, so the provider reads each of those with its default: a file published before they existed, or one that sets a single key under `tracing`, works. Then `definitions` (`'name' => Class::class`, or `'name' => [1 => Old::class, 2 => New::class]`: class names only, so `config:cache` works), `lease_timeout` (600, one value for every definition of the config), `connection` (null: the application's default connection), `queue` (`iq-php`), `observe_queue` (`iq-observe`) and `timeout` (300, at least 1). A registration that needs a closure or a lease of its own goes in a provider, on `IQ` itself, and is left out of the config. The provider registers it with `extend()` on the binding, not with `afterResolving()`: Laravel keeps a singleton before it runs the callbacks of `afterResolving()`, so a registration the SDK refuses there would throw once and leave every later job of the process an `IQ` without that definition. The file is published with the tag `iq-config` |
| Route and `EndpointController` | `POST /iq`, loaded with `loadRoutesFrom()`, outside every middleware group and with no name: the sync command builds the URL from the action of the controller. The provider gives `setEndpointUrl()` the same URL, from `APP_URL` and the path of the route, so that the endpoint answers a requested sync with what the command publishes, whatever host a request named. It does not look the route up: a provider of the application can build `IQ` before a route cache is loaded. The controller builds `IQ` inside a `try` and hands the request over: `$iq->handle($request->getMethod(), $request->headers->all(), $request->getContent())` into a `Response`. When `IQ` cannot be built, for want of the API key or for a registration the SDK refuses, the controller answers `503` with the code `unavailable` and a `Retry-After` of 5 seconds, as `handle()` does when the store fails, and reports the exception to the application's exception handler; a handler that throws does not change the answer. The platform then sends its message again and loses none. That answer comes before the signature is looked at, so a caller with no valid signature receives it too. Laravel answers before the controller is reached, with pages of its own that carry no `code`: its router answers `405` to a request that is not a `POST` (`200` to `OPTIONS`), and its global middleware `413` to a body longer than PHP's `post_max_size` and `503` in maintenance mode. The platform sends only `POST`s of under 4 KB, so it meets neither of the first two. It can meet the third: the simulator sends the message again by the status alone (the end of appendix B) |
| `Jobs\RunInvocation` | `ShouldQueue`, `$tries = 1`, `$timeout` from config, pushed through the bus onto `queue`. It holds the invocation as one string encrypted with the application key, so that neither the queue nor a job recorder such as Telescope stores an approval in clear. Beside that string it holds two numbers: its timeout, and how many copies were queued before it, which gives the delay of the next copy. While the job runs, PHP builds stack traces without arguments (`zend.exception_ignore_args`), so the trace of a job that timed out, which Laravel stores with the failed job, holds no input of the code it interrupted; the job gives the setting back when it ends. `handle()` builds `IQ` and calls `invoke()` inside a `try`, so the provider's `not_configured` is tried again like `invoke()`'s: a worker with no API key queues every segment again, those of the platform included. It fires `InvocationSettled` inside a `try` of its own: a listener that throws does not fail the job of a segment that ran, and its exception goes to the application's exception handler. On an `IQException` that 9.5 says to try again, it dispatches a fresh, delayed copy, then reports the reason and the class of the cause to the application's exception handler, never its message. Past the use-by time it fails instead, and the failed job names both; a reason 9.5 calls final fails it at once, also when it comes from building `IQ`, as for a registration the SDK refuses. On a queue that keeps no job for a worker (`sync`, `deferred`, `background`, a `failover` connection that falls back to one of them) Laravel does not wait for the delay of the copy: on `sync` the copy would run inside the job that queues it, and each copy would queue the next. There the job queues no copy and throws an `IQException` with the reason of the abort and the class of its cause, and with no previous exception: Laravel fails the job, `failed()` queues its observe, and on `sync` the caller of `dispatch()` receives `dispatch_failed`. A final reason and a passed use-by time fail the job there as on any queue. The job knows such a queue by the `SyncJob` that Laravel hands its handler. Laravel hands one also to a job that an application runs itself with `dispatchSync()`, `dispatchNow()` or `dispatchAfterResponse()`, whatever the queue of the bridge, and the job then throws in the same way; the bridge never runs its jobs like that. `failed()` only dispatches an observe, so a killed or timed-out job is reported as what the store shows, and the segment is never queued again from there. That observe is `Invocation::observeOf()` of the segment: it names the segment and says nothing of how it ended. The observe is pushed at once, whatever the connection's `after_commit` says: a timeout calls `failed()` inside the transaction the interrupted node holds, and that transaction never commits. Every other job of the bridge follows `after_commit`. A segment that fails ends its job normally and leaves no failed job. The job hands what the segment threw, which the report holds in `$exception`, to the application's exception handler before it fires the event: the handler treats it as the exception of any job, by its own rules. It does the same for an invocation of the platform that an exception of the application aborted. Whatever the job hands the handler, here and in every other place of both jobs and of the controller, a handler that throws in its turn fails nothing: what it throws ends there, because Laravel would store it with a failed job, and it can hold the message of what it was given |
| `Jobs\ObserveRun` | Carries announcements and observes, on `observe_queue`. It holds its notice as one encrypted string too, with a flag for the observe of a failed job whose listener has yet to be told, and the number of tries earlier jobs made. `$tries = 0`. `handle()` builds `IQ` and calls `invoke()` inside a `try`, like `Jobs\RunInvocation`. When `invoke()` throws `report_undelivered`, or any other reason that is not final, the job releases itself with the delays 10, 30, 60, 300, 900 s; a final refusal fails it, and so does a registration the SDK refuses while `IQ` is built. After 100 tries of one job a new, delayed job takes the notice over, because a queue may count the tries of a job in one byte, as the `jobs` table that Laravel 12 creates does. The new job carries the count of the tries made and is queued with the delay that count gives, so the notice goes on at 900 seconds and no worker takes it at once. A notice the platform did not record is tried again in silence. In a worker with no API key a notice follows the same rule, and each try is reported to the application's exception handler with the variable to set. `$backoff` holds the same five delays for a try that Laravel's worker releases itself: that is a job that throws anything that is not an `IQException`, such as one that cannot be read, and its tries are counted without the limit of 100. An observe that `failed()` dispatched fires `InvocationSettled` with its `observed` report, inside a `try` like the one of `Jobs\RunInvocation`, so a listener can close the stream of a killed or timed-out job. It fires at the first try whose report read the store, whether the platform recorded that report or not: `invoke()` throws with the report (9.5), and nothing local waits for the platform. A report that could not read the store tells no listener, and the same job is released for a later try. Once a report is fit to tell, the notice is handed to a new job that fires no event, because a release would put the same job back and tell the listener at every try, and the listener is told after that hand-over: a queue that takes no job then leaves this one to be tried again with its listener still to tell. On a queue that keeps no job for a worker a release keeps nothing: an undelivered notice is tried once and dropped, after its listener was told |
| `Events\InvocationSettled` | Carries the `Report` only. Fired once per segment that a job ran, and once more for the observe of a job that died or was kept aside as failed. That second event fires with the first `observed` report that read the store, also while the platform is away or refuses the API key. It can fire more than once: when the worker of the notice dies right after it fired, and when a person replays a notice that the platform had refused for good. A listener is idempotent. The report of a segment that failed in the worker holds what it threw, in `$exception`; a queued listener receives the report without it (section 4). The event is not fired for a segment run in a request with `run()` or `events()`. The application's hook to close a browser stream; a listener ignores a `refused` or `rejected` report whose code is `stale_attempt`, `stale_run` or `already_claimed`, which only marks a harmless second copy. The `run` of a report is the run that holds the workflow ID when the report was made: for an `observed` report that can be a later run than `runId`, so a listener compares the two before it acts on the status. An `observed` report of an answer or a signal of the application whose run is suspended does not say whether the message was applied (question 33): the listener closes the stream, and the browser loads the thread again. One of a start of the application with `claimed` true and no run does not say whether the turn ran: the listener closes the stream unless its own channel already delivered the end of that run |
| `iq:sync` | No argument and no option. Fails, before anything is sent, when the API key or the signing key is missing; when the queue connection the config names is not configured; when its driver is `sync`, `null`, `deferred` or `background`, or it is a `failover` connection that lists one of them, nothing, or a connection that is not configured; when `timeout` is under 1, which Laravel reads as no time limit; when `retry_after`, or the 60 seconds Laravel gives a `database`, `redis` or `beanstalkd` connection that sets none, does not exceed `timeout`, on the connection or on any connection a failover lists (a warning where the driver has no such setting); and when no `PersistenceInterface` is bound. One level of failover is read: a `failover` connection listed by another only gets the warning. The missing keys, the first fault of the queue and a missing store are printed together. `sync()` itself refuses a process with no definition registered and a URL to publish that is not `https`; the URL is built from `APP_URL`. Prints the URL and, from `IQ::definitions()`, the leases it publishes, says "nothing changed" when that is so, and reminds to restart the workers first: a worker still running old code cannot build a new version. Prints the versions the answer lists as retirable and, as a warning and not a failure, those it lists as stranded. A sync the platform did not confirm (`report_undelivered`) ends with "not confirmed: run the command again" and not with "nothing was published", because the platform may have applied it |

No `ShouldBeUnique` and no `WithoutOverlapping`: Neuron already refuses duplicates, and both either drop a redelivery after a kill or consume attempts.

Both jobs hold their invocation encrypted with `APP_KEY`. When the key is rotated, the old one stays in `APP_PREVIOUS_KEYS` until both queues have drained: a job encrypted with a key the application no longer knows cannot be read. A segment then fails its job without running and without a report, because `failed()` cannot read the job either, and a notice is released by Laravel's worker with `$backoff` and never fails. Both are read again once the old key is a previous key, and the failed segment is replayed with `queue:retry`.

The job of a start, an answer or a signal of yours that was lost with its worker stays in `failed_jobs`. Replayed with `queue:retry` within its use-by time, a start that was never claimed runs although its listener was told it was lost, and an answer or a signal is applied if its fence still holds; `InvocationSettled` then fires again. `queue:forget` removes the job.

Beside the pieces of the table, the public surface of the bridge holds `invocation()`, `displayName()` and `tags()` on both jobs, `$backoff` on `Jobs\ObserveRun`, and in the rows above the publish tag, the two default queue names and the variable of the platform URL. The constructors of both jobs are internal. The two jobs, the provider and the controller are not final, so their protected members can be overridden and count as surface too.

Some of this section was not run. On MySQL the 256th try of one job overflows a count kept in one byte: that is read from Laravel's source and was played on SQLite with a check on the column. On SQS a release is one more receive of the same message, so a redrive policy with a `maxReceiveCount` under 100 moves an undelivered notice to the dead-letter queue before a new job takes it over: that is read from Laravel's source and from what SQS documents of a redrive policy. The `background` queue, and a `failover` connection that falls back to `deferred` or to `background`, are held by no test: they were played by hand, the `background` queue once with real processes, and an aborted start ended by itself each time. On `deferred`, Laravel 12.69 does not run what a deferred job defers in its turn, so the observe of a job that failed there stays deferred and is not posted, where Laravel 13.35 runs it: that is read from Laravel's source. The `413` was not played. Octane was not run and its source was not read: a test plays the container of a request with a copy of the application.

## Appendix A. Wire protocol

JSON over HTTPS, `POST` only. Every request body carries `"protocol": 1`, except the sync request, and the ping answer and the answer to a requested sync, which list `protocols`. Receivers ignore fields they do not know. No message to the endpoint is longer than 65,536 bytes: a longer one is answered `400 invalid_request` and is not decoded (the largest valid message of protocol 1 is under 4 KB). Instants are Unix seconds. An integer is written without a fraction or an exponent: `1.0` and `1e0` are malformed (`400 invalid_request`; for `protocol`, `400 unsupported_protocol`), and in the answer to a sync they make the answer unusable. The full field tables and a JSON Schema per message are the first deliverable of the implementation (appendix D); this appendix fixes the shape.

| Identifier | Format |
|---|---|
| `definition` | `^[a-z0-9][a-z0-9._-]{0,63}$` |
| `workflowId` | Neuron's rule: 1 to 255 characters, no control character, no leading `__`. That is the engine's rule. `DatabasePersistence` and `EloquentPersistence` also refuse a partition name longer than 255 bytes, so on those stores a longer ID (multibyte characters) throws `PersistenceException` at every store operation: every `inspect` of it is answered `snapshotRead` false and every `abandon` `503 unavailable`, after its ledger entry was written |
| `runId` minted by the SDK or the platform | `<version>-<unique>`: `^[1-9][0-9]{0,5}-[A-Za-z0-9][A-Za-z0-9_-]{0,119}$`, such as `2-0192f3a8-7c1e-7d3a-9b1c-2f4e6a8c0d12` |
| Any other `runId` | Neuron's rule; it belongs to a run started outside the SDK and counts as the lowest version |
| `invocationId` | `^[A-Za-z0-9][A-Za-z0-9_-]{0,127}$`; for a platform message it equals the `webhook-id` header and is the same on every re-send |

The version a run is pinned to is the number at the front of its run ID. No message outside the sync carries a version field. `leaseSeconds` is the `leaseTimeout` given to `register()`.

### Authentication

| Direction | Rule |
|---|---|
| Platform to application | Standard Webhooks: headers `webhook-id`, `webhook-timestamp`, `webhook-signature` (`v1,<base64>`; several allowed, separated by spaces in one header value: repeated `webhook-signature` lines that a web server folds with a comma are not read as several). Signed text: `{id}.{timestamp}.{raw body}`, HMAC-SHA256, compared with `hash_equals`, timestamp within 300 seconds either way. The timestamp is read as a number, so one written with leading zeros is the same instant. A request with no `webhook-id` header verifies only when it was signed over an empty ID. The `webhook-id` of an `inspect`, an `abandon` or a `ping` is covered by the signature and not otherwise checked; that of a `start` or a `wake` is its `invocationId` and must have that format. The key is `whsec_` plus base64 and the SDK signs with the decoded bytes. A key that is missing, empty or does not decode is no key: every `POST` is answered `401` |
| Application to platform | `Authorization: Bearer <apiKey>`, `User-Agent: iq-php/<version>`, a 3 second timeout (15 for a sync and for the results of an evaluation). A `401` or `403` answer is final (`unauthorized`) |
| Both | HTTPS. `sync()` refuses, before anything is sent, an endpoint that does not begin with `https://`; local development needs an `https` tunnel, because the platform pings the endpoint before it accepts a sync. The platform URL is used as given: anything but `https`, outside local development, sends the API key in clear. The SDK's default client follows no redirect; a client you supply keeps its own policy |
| Rotation | The platform signs with every active signing key and accepts the old and the new API key during a rotation. The SDK holds one of each |

| Key | What its holder can do |
|---|---|
| Signing key | Inspect any workflow ID; read the manifest a sync publishes; wake a run, which forces a retry of a failed or dead one, or fires a due timer; abandon a run; start any registered definition whose default start event a node handles. On a run that carries a tag it inspects, wakes and abandons only through the definition that started the run (9.3); the exceptions are an abandon of a run whose records cannot be read in full, because its tag cannot be read either, and an abandon whose run took the workflow ID after the SDK had looked (below). The SDK cannot tell which definition started a run with no tag (appendix B, rule 3): a wake continues such a run on the nodes of whichever registered definition the message names, and an abandon that names another definition skips the guard of an Agent |
| API key | Publish a sync (definitions and endpoint), send announcements and reports, send traces and evaluation results |

```json
POST {platformUrl}/v1/sync
{"protocols": [1], "sdk": "iq-php/1.0.0", "endpoint": "https://shop.example.com/iq",

     "versions": [{"definition": "order-fulfilment", "version": 2, "openRuns": 14},

     "stranded": [{"definition": "trial", "version": 3, "openRuns": 2}]}
```

The list is complete and replaces the previous one. It names the definitions in the order they were first registered, and under each its versions in the order they were first registered. `sync()` refuses three things itself, with `invalid_request` and before anything is sent: a process that registered no definition, because an empty list would remove every version the platform holds and strand those with open runs, and a bootstrap that failed to register is the likeliest cause; an endpoint that does not begin with `https://`; and a registered lease under 60 seconds. Before applying the list the platform sends a signed `ping` to the endpoint and answers `422 endpoint_unverified` when that fails, so a wrong URL or key fails the deploy. An older version with no open run is retirable; the highest registered one never is. A stranded version left the code while runs remain; the sync is accepted anyway.

A `401` or `403` (`unauthorized`) and a `4xx` that carries `invalid_request`, `unsupported_protocol` or `endpoint_unverified` are final. A `200` is the answer to a sync only when its `modified` is a boolean and its `versions` and `stranded` are lists whose entries each hold a definition name, a version of 1 or more and a number of open runs of 0 or more; a list that is left out or null counts as empty, and `protocol` is not looked at. Any other answer, a `200` of another shape included, is thrown as `report_undelivered`: the platform did not confirm the sync, which may have been applied, and it can be run again because the list replaces the previous one. A version in the answer whose definition this process did not register is not an error: nothing of it is retirable here.

| Report field | Meaning |
|---|---|

### Platform to application: `POST {endpoint}`

```json
{"protocol": 1, "verb": "start", "invocationId": "inv_01JB2M", "definition": "nightly-reconciliation",
 "workflowId": "reconciliation:2026-10-07", "runId": "1-01JB2M8Q3W", "expiresAt": 1791368100}

{"protocol": 1, "verb": "wake", "invocationId": "inv_01JB7K4T9QW2", "definition": "order-fulfilment",
 "workflowId": "order:123", "runId": "2-0192f3a8-7c1e-7d3a-9b1c-2f4e6a8c0d12", "attempt": 1}

{"protocol": 1, "verb": "inspect", "definition": "order-fulfilment", "workflowId": "order:123", "runId": "2-0192f3a8-7c1e"}
{"protocol": 1, "verb": "abandon", "definition": "order-fulfilment", "workflowId": "order:123", "runId": "2-0192f3a8-7c1e", "attempt": 2}

```

| Verb | Fence | Runs in | Success |
|---|---|---|---|
| `start` | The run ID, minted by the platform with the current version, and `expiresAt`, 600 to 3600 seconds ahead; the endpoint checks only the upper bound (9.4) | The queue | `202` |
| `wake` | Run ID and attempt | The queue | `202` |
| `inspect` | None; `runId` is optional | The request | `200 {"run": {...} or null, "claimed": true, false or null, "snapshotRead": true, "at": ...}`; with `snapshotRead: false` when the store cannot be read |
| `abandon` | Run ID, and the attempt when the run exists | The request | The same body |
| `ping` | None | The request | `200 {"protocols": [1]}` |
| `sync` | None | The request | `200` with the body of the sync request above; `409 sync_refused` where `sync()` would throw before sending (9.4). An extension of protocol 1: an SDK that does not know it answers `400 invalid_request` |

**Abandon.** The SDK first looks at the run that holds the workflow ID. When that run carries a tag that is not the definition the message names, the answer is `400 invalid_request` and nothing is written, the ledger entry included: an abandon that names a plain definition cannot discard an agent's run that holds the workflow ID at that look. The look is made once: when the run it showed leaves and the run the message names takes the workflow ID before Neuron discards it, that run is discarded whatever its tag. A run with no tag is abandoned through whichever definition the message names, so the guard of an Agent then holds only when the message names the agent's own definition. Otherwise the SDK claims the run ID in the ledger when it is not there, with a use-by time one hour ahead, so that a start still waiting in the queue never runs. When a run held the workflow ID it then calls the workflow's own `abandon()`, which keeps an Agent's guard in force (answered `409 abandon_refused`). For an Agent the guard answers before the fence: a run suspended on a tool call nobody answered, which waits for an approval or a tool result, is `409 abandon_refused` also for a stale attempt and for the run ID of another run. A failed run has no such guard, whatever its conversation ends on: the agent answers the tool call it left as interrupted in its next turn. An abandon that carries no attempt discards the run with that run ID at whatever attempt it is. A run that is `running` with no lease is discarded like any other, and the process that executes it loses its next write. When no run holds the workflow ID it answers `200` with `run` null and `claimed` true if this call wrote the entry: the start will never run. A `200` after a run was discarded has the same body: a `200` says that nothing will run under that run ID any more, not whether anything ran. If the entry was already there it answers `409 stale_run` with `run` null, and the SDK cannot tell why: a job has claimed the start and its run is about to appear, the run has already ended, the start stopped between its claim and its first write, or an earlier copy of this abandon wrote the entry or discarded the run. The platform then inspects: when a run with that run ID is shown it abandons again with the attempt shown; when none is shown it closes the run as "ended, outcome unknown" (appendix B, rule 12). When a worker claimed and executed the start after the SDK had looked for a run, the same `409 stale_run` already shows that run, and the platform abandons again with the attempt shown. When another run holds the workflow ID the answer is `409 stale_run` with that run attached, whether this call wrote the entry or found it; when that run leaves while the abandon is dealt with and this call wrote the entry, the answer is the `200` of "no run". The code of a `409` is Neuron's refusal and `run` is read afterwards, so a run that ended in between gives `executing` or `conflict` with `run` null: the platform plans from `run`, never from the code. When the ledger cannot be read or written, the workflow cannot be built or the store fails while the run is discarded, the answer is `503 unavailable`. A run whose records cannot be read in full is still abandoned on its control record, as Neuron's own `abandon()` does: its tag cannot be read, so the definition the message names is not checked. When the run cannot be read for the answer, the answer carries `snapshotRead` false.

| Status | `code` | Meaning | The platform |
|---|---|---|---|
| `202` | | Verified, valid, queued; the body is `{}`. Nothing has run and no lease exists | Assumes nothing yet |
| `200` | | An `inspect`, an `abandon`, a `ping` or a `sync` was answered | Uses `run`; the answers to a `ping` and to a `sync` carry none |
| `400`, `405` | `invalid_request`, `unsupported_protocol` | Malformed, longer than 65,536 bytes, an unknown verb, an `inspect` or an `abandon` that names another definition than the one that started the run (nothing was written), or not a `POST` | Never re-sends; alerts |
| `401` | `invalid_signature` | One status and one code for every signature problem: the answer does not say which check failed | Stops deliveries, keeps timers, alerts; pings every 60 seconds and resumes after a successful `ping` |
| `404` | `unknown_definition`, `unknown_version` | This deployment lacks that code | Re-sends with a back-off while the version is in the latest manifest |
| `409` | A `RefusalReason` value, or `abandon_refused` | The run's state refused the abandon, or the run ID was already in the ledger and the SDK found no run holding the workflow ID (`stale_run`, with `run` null unless the run appeared afterwards); `run` is attached | Plans from `run` |
| `409` | `sync_refused` | This deployment would not publish the sync it was asked for; nothing is attached | Ends the request; a person runs the sync from the deploy |
| `503` | `dispatch_failed`, `unavailable` | The queue or the store failed, or the application's factory threw; `Retry-After` in seconds (5 today) | Re-sends the same message once `Retry-After` has passed, and holds back every other message to that endpoint until then |
| `500`, timeout, `3xx` | `internal_error` | Unknown | Re-sends the same message 5 times, with a back-off of 5 seconds that doubles to 300. Then it alerts and gives nothing up: a start or a wake counts as accepted and silent, and an `inspect` or an `abandon` is sent again at a slow pace (appendix B, rule 13) |

No answer of the endpoint carries `protocol`; every answer is a JSON object sent as `application/json`.

## Appendix B. What the platform must do

A run stays correct whatever the platform does with its clock, its memory and its timers. Five rules about how the platform writes its own orders are the exception, and the SDK cannot check them, except rule 3 for a run that carries a tag.

| # | Correctness depends on these |
|---|---|
| 1 | Never use a run ID twice. A start keeps one `expiresAt` for the life of its run ID, never more than 3600 seconds after the start is first sent: the ledger entry an abandon writes outlives the start only within that bound |
| 2 | A wake carries a run ID and an attempt that the application itself reported or returned from an `inspect` or an `abandon`. An abandon carries the same or, for a start the platform sent and has heard nothing of, that start's run ID with no attempt. Never guess or increment an attempt |
| 3 | Send a run its own definition: the one of the start the platform issued, or of the first announcement or report whose `runId` is that run. Never the definition of a message about another run. A run the platform has seen only in a snapshot, in a message about another run of that workflow ID or in the answer to an `inspect` or an `abandon`, is adopted under the `definition` the snapshot shows for it, when the manifest holds that definition: the platform then wakes it like any other run. When the snapshot shows null, or a definition the manifest does not hold, the run has no definition yet: send it nothing until an announcement or a report of its own arrives. Before it sends a wake, an `inspect` or an `abandon`, the platform compares the definition it would name with the one the last snapshot showed for that run. When they differ it sends nothing and alerts (rule 18); a snapshot that shows null leaves nothing to compare. For a run that carries a tag the SDK refuses a message that names another definition (9.3): a wake is reported `rejected: wrong_definition`, and an `inspect` or an `abandon` is answered `400 invalid_request`. For a run with no tag nothing checks this rule |
| 4 | One start per firing of a trigger |
| 5 | Abandon only when an operator asks |

Everything else is about getting a run woken at the right time and knowing when it ended.

6. **Plan from a snapshot that was read.** A snapshot that names a run replaces what the platform holds for that run when its attempt is higher, or equal with a later lease deadline or a status that left `running`. A report whose `snapshotRead` is false carries no snapshot: ignore its `run` and `claimed`, keep its outcome for rule 7, and `inspect` after 30 seconds, doubling to 600, until an answer is read.
7. **Know when a run has ended.**
   - A report closes the run named by its `runId` when its outcome is `completed`.
   - A snapshot that was read and shows no run, or another run, closes a run only if a snapshot named that run and every snapshot that named it is earlier: the run ended and the outcome is unknown. Earlier means a smaller `at`, whatever the order in which the snapshots arrived.
   - A run the application started may be known from its announcement alone. When `leaseSeconds` have passed since that announcement and no snapshot has named the run, `inspect`, and close it the same way if the answer shows no run, or another run. An announcement or a snapshot for that run with a later `at` opens it again.
   - A run may also be known from a snapshot alone, which names a run the platform has never heard of. When that snapshot shows a `definition` the manifest holds, the platform holds the run from then on, under that definition (rule 3), and closes it like any other run a snapshot named. When it shows null, or a definition the manifest does not hold, the platform holds nothing for that run.
   - An announcement never reopens a run closed as `completed`: a second copy of a start or of a wake posts its announcement before it is refused.
   - `rejected: already_claimed` closes nothing, and its snapshot is read like any other.
   - A wake reported `rejected: wrong_definition` is never sent again. It closes nothing, and its snapshot is read like any other.
   - A `200` answer to an abandon closes the run named in the abandon as abandoned, whether or not a snapshot ever named it. It is never shown as "never ran": the answer is the same when a run was discarded. A `409` answer is read like any other snapshot, and an abandoned start that it leaves open is asked about as in rule 12.
   - A start reported `refused`, `rejected: expired`, `rejected: invalid_start`, or `aborted` with `claimed` true is never sent again. If a snapshot that was read names its run ID, in that report or in an earlier one, or the run is already closed, the run exists or has existed: the report closes nothing by itself, and its snapshot is read like any other. Otherwise the start will never run under that run ID: mark it spent, and show the code to an operator when the platform issued the start. A start the application issued has no operator (question 6): it is marked spent and nobody is asked to act. `rejected: expired` is the exception, because it says only that this copy did not run: ask as in rule 12 before closing it.
   - What the platform concluded gives way to the store. A run closed as "ended, outcome unknown", as lost (rule 12) or as spent is open again when a snapshot with a later `at` than the message that closed it names that run, and the platform plans from that snapshot. A run closed as `completed` or as abandoned stays closed.
   - Instants are whole seconds, so a snapshot that names a run and one with the same `at` that does not name it cannot be ordered. The platform then neither closes that run nor opens it again: it plans no wake from what it holds for the run, and inspects once that second has passed.
8. **One timer per wait.** Send a wake at `wakeAt`. The same wait and attempt back, in the report of that wake itself (`suspended` with no `executedAttempt`), means "too early by the application's clock": try again after 1 to 60 seconds. What the platform still holds does not count: a wake whose own report shows no run, or anything but that wait and attempt, was not too early.
9. **Retries are wakes.** After a `failed` snapshot, wait by policy and send a wake with the attempt just reported. Count one failure per run ID and attempt. When the policy gives up, leave the run failed and alert.
10. **Silence means ask.** After an announcement, no report within `leaseSeconds`: `inspect`. After a `202` for a wake, no announcement within 900 seconds: `inspect`, and send the wake again when the attempt is unchanged. For a wake that rule 13 treats as accepted, the 900 seconds count from its last re-send. A wake may always be sent again, unless it was reported `rejected: wrong_definition` (rule 7); its fence makes copies harmless.
11. **A dead run is retried like a failed one.** When a snapshot shows `running` with a lease that has passed, send a wake with the attempt shown, under the same policy and count. A lease has passed when the `leaseExpiresAt` of a snapshot is not later than the `at` of that same snapshot: both are read on the application's clock, and the platform's own clock does not decide. When a snapshot shows `running` under a lease that has not passed, wait until the deadline (`leaseExpiresAt` minus that `at`, counted from when the snapshot arrived) and `inspect` if the platform still holds that snapshot: only a snapshot that shows the lease passed is followed by a wake. Never send a wake to a running run before its lease deadline, and never to one shown `running` with no lease: it was started outside the SDK. Read it now and then, and alert.
12. **A start that stays open is asked about, not replaced.** When a start is still open at its `expiresAt` plus 300 seconds, because it stayed silent or because its reports closed nothing, `inspect` with the run ID. If the run holds the workflow ID, plan from the snapshot. If it does not and `claimed` is false, no copy claimed it and none can any more: close it as lost. If it does not and `claimed` is true, close it as "ended, outcome unknown": it completed without a report, was abandoned, or stopped before its first write, and the answer cannot tell which. Both are shown to an operator when the platform issued the start, the second with the warning that the workflow may have run; a start the application issued has no operator (rule 7). An `inspect` made later than `expiresAt` plus 3600 seconds can answer `claimed: false` for a start that ran, because its entry may have been dropped: treat that as outcome unknown too. The platform never issues a replacement on its own. An `inspect` answered `400` shows nothing of the start: a run that another definition started holds the workflow ID, and the platform alerts (rule 18).
13. **Re-send only what can be re-sent**, and only a message the platform itself sent, never a segment the application issued: after a `503`; after a `500`, a `3xx` or a timeout, 5 times; a `404` for a version in the manifest, an `aborted` report whose `claimed` is not true, or an `observed` report or `inspect` answer for a start the platform issued that shows `claimed: false` and no run under its run ID. In an `aborted` report a `null` is re-sent like a `false`: a copy of a start that was in fact claimed is `rejected: already_claimed` and changes nothing. An `observed` report or an `inspect` answer whose `snapshotRead` is false shows nothing and falls under rule 6. An announcement or a report that carries the `invocationId` of a message shows that the message was queued, whatever the endpoint answered: after a `500`, a `3xx` or a timeout the platform need not send it again, and a copy it does send is harmless. After the last of the 5 re-sends of a start or a wake the platform does not end it. It alerts, and treats the message as accepted and silent: rule 10 then asks about a wake after the wake silence and sends it again when the attempt is unchanged, and rule 12 asks about a start after its use-by time. An endpoint that cannot be reached for a while, as during a deploy or a restart of the web tier, therefore never loses a timer: the wake leaves once the endpoint answers again. An `inspect` or an `abandon` that gets a `500`, a `3xx` or a timeout is sent again the same way. After its last re-send the platform alerts and sends it again at a slow pace until an answer is read: neither is forgotten. A message answered `503` is sent again once its `Retry-After` has passed. Any other message waits for a back-off of 5 seconds that doubles to 300, and so does one answered `503` with no `Retry-After`. A start is never sent after its `expiresAt`.
14. **Read a wait that has no timer now and then.** A run suspended without `wakeAt` is inspected daily at first, then less often, at least every 7 days. This is how the platform notices a run that was abandoned, reset or answered without a report.
15. **Keep only coordination data** from what the application sends, and answer `recorded: true` only after a durable write. That covers the platform's logs: a field it does not know is dropped, and a body is not kept as it arrived. Accept announcements and reports for runs it did not start: the application wins.
16. **Sync.** Ping the endpoint first. Accept only `https` endpoints that are publicly routable, and never follow redirects. Ask an owner to confirm before moving an environment's endpoint to another host. Never invoke a stranded version.
17. **Do not flood.** Limit the requests in flight to one endpoint, honour `Retry-After`, which holds back every message to that endpoint, and spread out timers that come due together after an outage.
18. **Alert** on an announcement or a report whose `origin` is `platform` and whose `invocationId` the platform never sent, which is a start or a wake it never issued (the signing key may have leaked), on a wake reported `rejected: wrong_definition` and on a `400` answer to an `inspect` or an `abandon` (the platform named a definition that did not start the run, or someone else holds the signing key), on a wake, an `inspect` or an `abandon` it does not send because the last snapshot of the run shows another definition (rule 3), and on a report whose `at` is more than 300 seconds from its own clock.

What this appendix does not settle yet, beyond questions 15, 17 to 19, 21 and 22 of section 2. The simulator makes a choice for each, named here, so that the engineer who builds the platform knows where the text stops:

- **Answers the status table does not list**: a refused or reset connection, a TLS or DNS failure, `403`, `408`, `429`, `502`, `504`, another `2xx`, a `200`, `202` or `409` whose body is broken, and a `404` or `503` with no `code`, which is what a proxy in front of the application answers. The table does not say whether the status or the code decides. The simulator reads the body of a `200` and of a `409` only, so the status decides for the rest. A `202` to a start or a wake counts as accepted whatever its body. A `404` or a `503` with no `code` is sent again as the table says for that status. The simulator treats every other answer of the list like a `500`: sent again 5 times, then as rule 13 says. What rule 13 promises for an endpoint that cannot be reached rests on these choices, because a web tier that is down answers with a refused connection or with the `502` or `503` of a proxy.
- **An `inspect` or an `abandon` that fails.** Rule 13 now says what follows the last re-send of an `inspect` or an `abandon`: it is sent again at a slow pace and is not forgotten. The pace has no value (the simulator: every 300 seconds, the cap of the back-off). Whether "never re-sends" after a `400` or `405` means the run is never asked about again is not said. After a `400` to the inspect of rule 12 the start stays open, and its version is never retirable.
- **A start whose re-sends ran out.** Rule 13 treats it as accepted and silent, and rule 12 asks about it after its use-by time, when it can no longer be sent: an endpoint that cannot be reached for longer than the re-sends last, 155 seconds, still loses a start sent in that time, although its use-by time has not passed. Whether the platform should ask sooner is not said. The simulator asks about such a start after the wake silence too, while its use-by time has not passed, and sends it again by rule 13 when the answer shows it unclaimed with no run. With the values of the Durations table that reaches only a start whose use-by time is more than about 20 minutes ahead: 155 seconds of re-sends, 900 of silence and one back-off.
- **An abandon of a run the platform has heard of and holds no attempt for** (announced only, or reported with no run): rule 2 allows neither form. The simulator sends the abandon with no attempt for a start the platform sent, and refuses the operator's request for a run the application started.
- **An abandon answered `409 abandon_refused`.** Appendix A says the platform plans from `run`, and no rule says what becomes of the operator's request when the guard of an agent refuses it. The simulator ends the request as refused on that code and does not send the abandon again.
- **Rule 10.** Whether `leaseSeconds` are counted from the `at` of the announcement or from its arrival, which differ when a queue posts the announcement late (the simulator counts from `at`); whether a silent announcement of a run the platform holds closed is asked about; and what follows the inspect after a silent segment when it shows the same wait and attempt.
- **Stranded versions and rule 16.** What becomes of the due timers of a stranded version; what "another host" is (the host, or scheme, host and port); and when "publicly routable" is checked (at the sync only, or at every delivery).
- **Periods without a value.** "Read it now and then" in rule 11, and the shape of "daily at first, then less often" in rule 14 (the simulator reads after 1, 2, 4, then every 7 days). How many times an abandon is sent again after a `409` that shows another attempt (the simulator: 5). Whether a snapshot that shows a run `completed`, a completion retained outside the SDK, closes it.
- **A wake whose report shows that nothing ran.** Rules 8, 10 and 13 name three wakes that are sent again: one that came too early, one that stayed silent and one reported `aborted`. No rule says whether a wake is sent again when its report is `refused: conflict`, or `observed` for a worker that died before the wake was admitted, and the snapshot still shows the wait or the failed attempt the wake was sent for. The fence makes a copy harmless. The simulator sends the wake again after the back-off and counts no new failure.

`PLATFORM_PROTOCOL.md` describes the platform's side for whoever builds it, and its section 11 holds the full list under its own numbers: Q1 to Q6 are questions 15, 17, 18, 19, 21 and 22, U1 to U27 are the points the rules do not settle, of which the list above names the first found, and P1 to P7 are what the platform's product decides and the protocol does not.

## Appendix C. Testing support

Shipped in `src/Testing`, in neuron-ai's "queue responses, record calls, assert" style.

```php
class FakePlatform implements HttpClientInterface
{
    public readonly string $signingKey;
    public function failNext(int $times = 1, int $status = 503): static;
    public function deliver(IQ $iq, array $message, ?int $timestamp = null): HttpResponse;   // signs, calls handle()
    public function wake(IQ $iq, string $workflowId): HttpResponse;    // fences from the last report
    public function assertSynced(): void;
    public function assertAnnounced(string $workflowId, ?Verb $verb = null): void;
    public function assertReported(string $workflowId, Outcome $outcome, ?string $code = null): void;
    public function keepDataset(string $slug, array $items): static;   // answers GET /v1/datasets/{slug} with these items
    public function assertTraced(string $rootSpan): void;              // a trace taken in has a parentless span of this name
    public function assertEvaluated(string $evaluator): void;          // the results of this evaluator class were taken in
}   // it takes a trace and the results of an evaluation in with a 200, as the platform does

class FakeDispatcher implements DispatcherInterface
{
    public function assertDispatched(Verb $verb, ?string $workflowId = null): void;
    // Runs what is queued through invoke(), each message $times times: 2 proves a second delivery harmless.
    // Like a worker, it keeps queued a message invoke() threw for, unless it is final or past its expiresAt.
    public function runAll(IQ $iq, int $times = 1): array;   // what each invoke() returned (a Report) or threw (an IQException)
}
```

A test shares one `InMemoryPersistence` through `setPersistence(fn () => $store)`. A test that calls `sync()` uses SQLite `DatabasePersistence` instead, because `sync()` refuses the in-memory store, and registers leases of 60 seconds or more (the default is 600), because `sync()` refuses a shorter one. Neuron reads `time()` directly, so tests use past deadlines and short real leases, never a fake clock.

The fake answers a sync with no open run on any version and nothing stranded, and does not ping the endpoint: `failNext(1, 422)` plays a ping that failed. `deliver($iq, ['verb' => 'sync'])` plays a sync the platform asks for, and returns the endpoint's answer. `wake()` fences from the last report the fake recorded for the workflow ID and takes the definition from that report. Each call sends a new invocation ID, so two calls are two wakes, not one wake sent again. It fails the test when no report was recorded for the workflow ID or the last one shows no run. A dead run, which posts no report, is woken with `deliver()` from an `inspect` answer.

The fake also stands in for the platform of tracing and evaluation. `assertTraced()` looks at every trace it took in, through `resourceSpans`, `scopeSpans` and `spans`, for a span with no parent whose name is the one given: `invoke_agent <name>` for an agent and `invoke_workflow <name>` for a workflow, where the name is the short class name for a run the application runs with a `tracer()` listener (`invoke_agent SupportAgent`) and the definition name for a segment the SDK executes (`invoke_workflow order-fulfilment`, `invoke_agent support-agent`). A span with no `parentSpanId`, or an empty one, has no parent. `assertEvaluated()` looks for the evaluator class in the `name` of the results the evaluation output posted, and passes for an evaluator that could not run, whose results the output posts with its error. Both count no request that `failNext()` refused, as the assertions above do, and a failure names what the fake took in. `keepDataset()` keeps the items of a slug, as a list, each as the platform answers an item: `dataset_item_id`, `input` and `expected_output` alone, the ID the position of the item from 1 and the rest null when it was not given. From then on a read of `/v1/datasets/{slug}`, with the slug decoded as the SDK encodes it, is answered `200` with `slug`, `name` (the slug), `description` (null) and `items`, as the platform answers. A failure `failNext()` queued comes first, so `failNext(1, 503)` plays a platform away when the dataset is read and the next read gets the items. A slug the fake was not given is answered `404`, which `load()` throws as `report_undelivered`. The fake answers by path, whatever the method.

A test of an `InvocationSettled` listener takes its `Report` from `invoke()` or from `FakeDispatcher::runAll()`. For the report of a job that died, `invoke()` is given `Invocation::observeOf()` of the segment, which a test of a Laravel application reads from the queued job with `invocation()`. The constructor of `Report` stays internal. On Laravel's `sync` queue, which the `phpunit.xml` of a Laravel application sets, a dispatched segment runs before `dispatch()` returns. An aborted one makes `dispatch()` throw `dispatch_failed` after `InvocationSettled` fired once with the `observed` report of its failed job. The exception before it is the bridge's: it names the reason of the abort and the class of its cause, never its message (section 10). To read the cause itself, a test queues the segment on `Queue::fake()` and gives the `invocation()` of the job to `invoke()`: the exception the SDK throws carries the cause as its previous. A notice the platform does not record is tried once on that queue and dropped.

A test that runs a platform simulator beside the application on one machine cannot publish the address the application listens on: `sync()` publishes only an `https` endpoint, and the platform accepts only a publicly routable one (appendix B, rule 16). The application publishes a public `https` URL, and the simulator is told which local `http` address stands behind that origin, as a tunnel does in local development (appendix A).

Seven limits of the checking are worth knowing.

- **The Symfony bridge is not built, and nothing ran against a real platform.** Every part of section 9 is implemented and tested, and so is the Laravel bridge of section 10. The Symfony bridge is still text. The endpoint and `sync()` ran against the fake, against scripted HTTP answers and against the simulator. A streamed turn ran over real HTTP on PHP's built-in server only: in one test of the SDK, and in the end-to-end tests of the Laravel bridge.
- **The tests ran on PHP 8.4 and 8.5, not on 8.1.** The local 8.1 build lacks the extensions PHPUnit needs, so on 8.1 the code is proven by lint, by PHPStan set to 8.1 and by a small in-memory script. CI runs the full matrix. The same holds for the Laravel bridge on PHP 8.2, its lowest: lint and PHPStan set to 8.2, and no PHP 8.3 was at hand.
- **The Laravel bridge ran on the database queue on SQLite only.** Nothing ran on MySQL, PostgreSQL, Redis, SQS, Horizon or Octane: what section 10 says of them rests on reading Laravel's source and, for Octane, on a test that plays a container of the request. Its end-to-end tests need PHP 8.4, and ran on Laravel 13.35.0, on 12.69.0, which is the lowest release Composer installs by default today, and on 12.41.0, the declared floor (question 23). The Symfony bridge ran against the first design, over a stub of its core, with the Doctrine transport: the rows this revision changed have not been run.
- **One case of a stream still depends on a setting of PHP.** `zend.exception_ignore_args` is on in PHP's production ini and off in PHP itself and in its development ini. Every suite of the SDK now passes with either value, and tests hold that the SDK keeps no exception that would keep a workflow alive after its report or its stream is released. What still depends on the setting is a stream left on an error frame whose failure a listener of the application hid from the SDK: its observe is handed over when PHP destroys the stream, which with the setting off is when PHP collects cycles or the request ends (9.6, question 38). The end-to-end tests of the bridge ran with the setting on only, as the processes they start read the ini of this machine.
- **Traces and evaluation results were checked against the SDK's own reading of them.** No OpenTelemetry collector and no platform received a trace: the tests read the OTLP request the SDK builds and the evaluation message it posts. RAG retrieval, parallel branches, middleware and structured output are mapped by the listener and have no test here: the agent of the tests calls one tool. The trajectory of a conversation as the output of an evaluation has none either.
- **Concurrency was not run on every backend.** The built code ran its multi-process tests on SQLite. The prototype's ledger also ran on MySQL, Postgres and Redis; nothing ran on the Eloquent backend.
- **The platform does not exist, and its rules are not final.** Appendix B is now followed by a simulator that speaks the protocol over real HTTP, independently of the SDK's code, and one end-to-end test plays each row of section 7 with real processes. Building it showed where the appendix was silent or led to a wrong result: the clear cases are corrected in the text, eight became questions 15 to 22 of section 2, of which 16 and 20 are decided and applied, and the rest is listed at the end of appendix B. The simulator is a test instrument: it follows most rules as written and a few only in the cases its tests play. The end-to-end tests of the Laravel bridge run against the same simulator.
